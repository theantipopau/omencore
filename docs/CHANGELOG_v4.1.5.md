## Fixed: GPU Power Boost Never Worked on Victus 16-d1176TX (board `8A25`)

Same reporter (Discord, ACe_Centrick) filed this on three consecutive versions — v3.8.0, v4.0.0, and v4.1.0 — each time getting the same `GPU Power Boost: skipped — HP Victus does not support WMI TGP/PPAB control` log line, despite reporting that older OmenCore versions and OMEN Gaming Hub both successfully boost their RTX 3060 from 85W base TGP to 100W on the same hardware. One independent corroboration (OsamaBiden) on the same board family.

4.1.0 already fixed the *architecture* gap this depended on (the blanket Victus vendor-family deny now yields to an explicit per-model `SupportsGpuPowerBoost = true` opt-in), but no Victus board had that flag set, so behavior didn't change. This release adds the flag: a dedicated `ProductId = "8A25"` model-database entry (this exact board previously had no entry of its own — both field logs show `Found model by model-name pattern '16-d1' (no entry for ProductId '8A25')`, meaning it was silently inheriting the unconfirmed `8A26` sibling entry) with `SupportsGpuPowerBoost = true`. The `8A26` entry itself is untouched and still `false`.

This is a judgment call made after three consistent reports with no counter-evidence, rather than after receiving a session log with explicit before/after wattage figures — flagged transparently rather than claimed as field-log-proven. 2 new tests confirm the new entry resolves by exact ProductId ahead of the shared `16-d1` name pattern, and that it's independent of `8A26`.

## Fixed: Locked Fan-Curve Tooltip Read as "Not Verified" Instead of "Not Supported"

GitHub #156 (and its earlier #149) both center on a reporter trying to "force-verify" their OMEN Transcend 14 (board `8C58`) profile so custom fan curves would unlock. Traced the code: curve availability (`FanService.FanCurvesAvailable`) is gated purely by the `SupportsFanCurves` capability flag, completely independent of `UserVerified` — this board's `SupportsFanCurves = false` because Transcend 14 exposes a WMI profile-only fan interface, not a real curve API, same as its `8E41` sibling. The "unverified" status the reporter kept asking about has nothing to do with why curves are locked.

The Diagnostics tab already carries correct explanatory copy for this distinction; the locked Custom/Direct fan-control tiles elsewhere in the app didn't. `FanControlViewModel.CustomCurveTooltip`/`DirectFanControlTooltip` now explicitly state the limitation is a hardware/firmware capability, not related to verification status, instead of the ambiguous "unavailable for this model." Pure UI string change — no control-availability logic changed.

## Fixed: `ApplyMaxCooling()` Silently Reported Success Even When the Hardware Write Failed

Found during a broader audit of fan-control/RGB code for the same "logs success without confirming a real write happened" bug class already fixed once this cycle (the Logitech HID++ fallback). `IFanController.ApplyMaxCooling()` returned `void` — its three real backends (WMI, EC, OGH proxy) all had a real success/failure result available (`SetMaxFanSpeed`, `SetMaxFan`) but discarded it before it ever reached the interface boundary. `FanService.ApplyMaxCooling()` then unconditionally set its internal fan-mode field to `"Max"` and logged `"Max cooling mode active"` regardless of whether the write actually succeeded.

This is safety-relevant: `MainViewModel.OnQuietSafetyOverrideActivated` — the handler that fires when temperature crosses into critical territory while in Quiet mode — calls `ApplyMaxCooling()` and then reads `FanService.GetCurrentFanMode()` back as its confirmation that the emergency response took effect. Because that field was set unconditionally, the confirmation was circular: a transient WMI busy error during a genuine thermal emergency would leave fans unchanged while the log, the UI, and the "confirmation" all agreed nothing was wrong.

**Fix:** `IFanController.ApplyMaxCooling()` now returns `bool`, propagated honestly from all four backend implementations (WMI, EC — which already computed but discarded this result, OGH proxy, and the no-backend fallback, which now correctly returns `false`). `FanService.ApplyMaxCooling()` only marks Max mode active and logs success when a write actually succeeded (either the controller call itself, or — for non-WMI backends only — the existing defensive `SetFanSpeed(100)` fallback); on failure it logs a warning and records the failure in fan-command history instead. `MainViewModel`'s safety-override handler now surfaces a distinct warning toast ("temp critical, but Max cooling failed to apply") instead of unconditionally claiming success. 19 test-fake `IFanController` implementations across the test suite were updated for the new interface signature (all continue returning `true`, preserving existing test behavior); 1 new regression test (`ApplyMaxCooling_ControllerReportsFailure_DoesNotClaimMaxModeActive`) pins the fixed behavior on the WMI backend path specifically, since non-WMI backends already had a working fallback that happened to mask this bug.

**Scope note:** `ApplyAutoMode()`/`ApplyQuietMode()` on the same interface have the identical `void`-return shape and were flagged during the same audit, but were left unchanged this release — narrower scope, matching what was actually requested.

## Fixed: Razer RGB Effects Reported Success Even When Nothing Was Written

Same bug class as the Logitech HID++ fallback fixed earlier this cycle, found during a follow-up audit of the other RGB providers for the same shape. All six `RazerService` effect setters (`SetStaticColor`, `SetBreathingEffect`, `SetSpectrumEffect`, `SetWaveEffect`, `SetReactiveEffect`, `SetCustomKeyboardEffect`) fell through to an unconditional `return true` whenever there was no active Chroma SDK session — including "basic mode" (Razer Synapse detected but no SDK session established), which has no alternate write path anywhere in the class. A user with Synapse installed but no Chroma session running would see every lighting command log as applied while nothing happened on the actual hardware.

**Fix:** each setter now returns `false` and logs a warning distinguishing "no active session, nothing to write" from "write attempted and failed," instead of masking both as success. Separately, `RazerRgbProvider.ApplyEffectAsync` only matched the literal strings `effect:spectrum` and `effect:wave` from the documented `effect:<name>` contract (see `IRgbProvider.ApplyEffectAsync`'s doc comment) — `effect:breathing`, `effect:static`, `effect:off`, and `effect:rainbow` fell through to a silent no-op. Replaced the two hardcoded checks with a generic `effect:` prefix switch covering the full contract, matching the pattern `CorsairRgbProvider` already used. No test coverage added — `RazerService` has no mockable HTTP abstraction (same reason `LogitechHidDirect` had none), verified by build-clean + code review only.

## Fixed: Corsair RGB Write Failures Were Indistinguishable From Success

Traced through all three `ICorsairSdkProvider` backends (`CorsairSdkStub`, `CorsairICueSdk`, `CorsairHidDirect`): `ApplyLightingAsync` returned plain `Task`, so every per-device write loop in `CorsairDeviceService` (`ApplyLightingToAllAsync`, `ApplyBreathingToAllAsync`, `ApplySpectrumToAllAsync`, `ApplyWaveToAllAsync`, `ApplyLightingPresetAsync`, `ApplyPerformanceModePatternAsync`) treated "the call didn't throw" as success — but the real iCUE implementation catches its own exceptions internally and just logs (never rethrows), and the same for the direct-HID implementation's outer `ApplyLightingAsync` wrapper. A device the iCUE RGB.NET surface couldn't find, or a HID write that failed after its internal retries, would still be counted as a successful write. Every affected method then unconditionally logged `"Applied ... to N device(s)"` regardless of how many of those N actually succeeded — the exact bug class already found and fixed in `RazerService` and `LogitechHidDirect` this cycle, just one layer deeper (the failure was swallowed inside the SDK implementation, not inside the calling loop).

**Fix:** `ICorsairSdkProvider.ApplyLightingAsync` now returns `Task<bool>`, propagated honestly from all three implementations (the stub always succeeds; the iCUE and direct-HID implementations return `false` on a not-found device or a caught exception instead of silently swallowing it). All six `CorsairDeviceService` methods now count real successes instead of non-throws, and log an accurate `N/M succeeded` (or an explicit "all writes failed") instead of always claiming full success. 1 new regression test (`ApplyLightingToAllAsync_SdkReturnsFalse_ReportsFailureInsteadOfClaimingSuccess`) pins this using the existing mockable `ICorsairSdkProvider` test fake.

## Fixed: MainWindow's "Unsupported or Unverified" Banner Conflated Two Different States

The single warning banner shown for non-supported systems had its `Visibility` gated only on `!SystemInfo.IsHpGaming`, but its text claimed to also cover "an unverified model fallback." In practice: a genuinely supported HP OMEN/Victus whose specific SKU just isn't in the field-verified capability database got **no banner at all**, despite the text implying it would; a non-HP system saw wording that could be misread as "might still work, just unverified" when the system is actually unsupported outright. This is the same conflation pattern already fixed once this cycle in the locked fan-curve tooltip (#156/#149) — this time one level up, in the top-level system-status banner.

**Fix:** split into two independently-gated banners on `MainViewModel`: `ShowUnsupportedSystemBanner` (true only when the system isn't HP OMEN/Victus at all — "most hardware-control features will be unavailable, this is a hardware/firmware limitation") and `ShowUnverifiedModelBanner` (true when it *is* a real HP OMEN/Victus but the model is either not in the capability database at all or has a database entry that isn't yet `UserVerified` — "capabilities are inferred rather than confirmed, most functionality should still work"). 6 new tests cover both flags independently across the not-HP-gaming / known-unverified / unknown-model / known-and-verified combinations.

## Fixed: `SettingsView.xaml` Accessibility Labeling Was Half-Finished

An accessibility pass across five views in an earlier cycle explicitly left `SettingsView.xaml` partially done (53 of 156 interactive controls labeled). Audited the remaining 103 — 36 `ToggleButton`, 29 `Button`, 19 `ComboBox`, 16 `TextBox`, 9 `Slider`, 2 `CheckBox` — and added `AutomationProperties.Name` to every one, using each control's actual adjacent visible label (a preceding title-style `TextBlock`, or a `Button`'s own `Content` text with any leading emoji stripped) rather than a name paraphrased from its binding path. A handful needed manual correction where the nearest text in the markup wasn't the real label — e.g. a conditionally-visible "✓ Active" status badge sitting between a toggle and its actual "Stay on top" title, three icon-only quick-link buttons whose visible text lives in a child `StackPanel` rather than a `Content` attribute, and the two icon-only "✕" remove buttons in the scheduler/automation rule lists, which now read as "Remove Schedule Rule" / "Remove Automation Rule" instead of an unlabeled ✕. `SettingsView.xaml` is now the sixth and final view with full interactive-control coverage. Verified via an XML well-formedness check, a full build, and manual spot-checks across the OSD metrics block, the cleanup-toggle block, and both rule-list templates — no screen reader was available in this environment to verify the announced names end-to-end, flagging that gap rather than overclaiming, consistent with how the earlier four-view pass was verified.

## Not Actioned This Release (Found During the Same Audits, Deliberately Deferred)

Lower-confidence or larger-scope findings from the same fan-control/RGB audit passes, not acted on this release:

- **`FanService.cs`'s curve-ramp task can race itself.** A fire-and-forget `RampFanToPercentAsync` call is started inside `_curveLock` but the lock releases before the ramp finishes; if the next curve tick computes a new target before the prior ramp completes, both read/write the shared last-applied-percent field from their own stale snapshot. Plausible cause of the "sometimes glitchy" fan-speed reports seen in the field, but needs a real double-buffering fix, not a one-line change — flagged for a dedicated pass rather than rushed alongside this release's other fixes.
- **`WmiFanController`'s Max-mode keepalive timer bypasses `FanService`'s write-serialization lock entirely.** The countdown-extension timer writes directly to the WMI BIOS interface on its own schedule, with only a reentrancy guard against itself — a user-issued fan command at the same instant the timer fires isn't excluded by the same lock that serializes every other fan write path (`_fanWriteLock`/`RuntimeEcOperationCoordinator`). Same shape as the Max-mode reassert bug already fixed this cycle, on the write side instead of the read side.
- **Inconsistent hardcoded RPM ceilings** — `WmiFanController.ReadFanSpeeds()` clamps duty% against a fixed 5500 RPM divisor while `EstimateDutyFromRpm` uses 6000, and other comments in the same file note boards reaching 6300 RPM. On boards with a real ceiling above 5500, displayed duty% pins at 100% before the fan physically maxes out.
- **`RazerRgbProvider`/`CorsairRgbProvider`'s `SetStaticColorAsync`/`SetBreathingEffectAsync`/etc. convenience methods** still don't check or log the honest success/failure value their underlying calls now return (`RazerService.SetStaticColor` and `CorsairDeviceService.ApplyLightingToAllAsync` both now return `bool`) — only the `ApplyEffectAsync` dispatch path fixed this release does. A caller using these convenience methods directly still can't tell success from failure.
