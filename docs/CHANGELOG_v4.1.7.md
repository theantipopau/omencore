## Fixed: Unconfirmed EC Power-Limit Register Writes Were Attempted by Default

`PerformanceModeService.DirectEcPowerLimitWritesBlocked` gated `PowerLimitController`'s CPU PL1/PL2 and GPU TGP writes on `ModelCapabilities.SupportsFanControlEc` — a flag that also controls real, working EC fan control on many boards and **defaults to `true`**. `PowerLimitController`'s own header comment already documents its EC register addresses (`0xC0`-`0xC5`) as unconfirmed: `// HP Omen EC register addresses (EXAMPLE - varies by model!)`, with an explicit warning that incorrect values `can cause system instability or hardware damage`. Reusing the fan-control flag as the gate meant any board whose database entry didn't explicitly opt out got this unconfirmed, higher-risk write path attempted by default — including boards that have never had these specific register addresses confirmed for their hardware.

Found by tracing GitHub #159 (ShantanuVasagadekar, OMEN 16-n0xxx AMD, board `8A44`): Performance Mode logged `Power limits applied: CPU=95W, GPU=140W` and reported success unconditionally, while the reporter's measured GPU power stayed well below a previously-observed baseline (~75W vs. ~115-120W they'd seen on the same hardware before).

**Fix:** added a new, dedicated `ModelCapabilities.SupportsEcPowerLimits` flag, defaulting `false` and fully decoupled from `SupportsFanControlEc`. `PerformanceModeService.DirectEcPowerLimitWritesBlocked` now checks the new flag instead of the shared one — every board's unconfirmed EC power-limit write path is blocked by default (fail-safe) until a model's real register addresses are confirmed and the flag is deliberately set `true` on that entry. No existing `ModelCapabilities` entry sets it today, so this is a pure safety tightening, not a regression for any currently-shipping board — the EC power-limit write path has never been confirmed correct for any model in this database. Real EC fan control (a completely different, already-working feature on many boards) is untouched, since it no longer shares a gate with this. 2 new tests: one confirms a board with `SupportsFanControlEc = true` (real fan control works) still blocks EC power-limit writes when `SupportsEcPowerLimits` is left unset; one confirms the explicit opt-in still works.

## Fixed: GPU Power Boost Status Text Claimed "NVAPI Power Limits Available" When They Weren't

`SystemControlViewModel`'s GPU Power Boost status message had a branch that appended `" (NVAPI power limits available)"` whenever `GpuNvapiAvailable` was true — but that property only means NVAPI itself initialized (a GPU was detected via NVAPI), not that power-limit writes are actually supported. The correct property for that, `GpuPowerLimitAvailable`, already existed and was used correctly one branch above it. GitHub #159 showed exactly this mismatch in practice: the log reported `NVAPI: NVAPI returned no writable power policy entries` and `Supports Power Limit: False`, while the UI simultaneously displayed the misleading "available" note.

**Fix:** the branch now checks `GpuPowerLimitAvailable` instead of `GpuNvapiAvailable`, matching the property that's actually being described. Pure text-logic fix, no control-availability behavior changed.

## Fixed: Switching Performance Mode While Max Fans Was Active Left Fans Stuck at Maximum

Reported by Discord user SAINTOP (HP Victus 15 fa2082wm, board `8DCD`): enabling Performance Mode + Maximum Fans worked as expected, but switching back to Balanced — from either the General tab or Custom tab with fan control set to Auto — left the fans running at maximum speed. Only fully closing OmenCore released them. A related symptom was also reported: after eventually reaching Auto via Quick Access, fans would later spike to maximum and cycle repeatedly between maximum and auto on their own.

**Root cause:** `WmiFanController.SetPerformanceMode(string)` sent `_wmiBios.SetFanMode(...)` and, on success, cleared the internal `_isMaxModeActive`/`IsManualControlActive` tracking flags — but never sent `_wmiBios.SetFanMax(false)`. These are two independently-required BIOS commands (`ResetFromMaxMode()`'s own Step 1/Step 2 structure already establishes this). With the flag falsely cleared, every subsequent `RestoreAutoControl()` call saw `_isMaxModeActive == false` and skipped the reset that would have released the real hardware latch — matching the report exactly, since both the General-tab Balanced switch and the Custom-tab Balanced+Auto switch route through `SetPerformanceMode` first.

**Fix:** `SetPerformanceMode` now sends `SetFanMax(false)` before clearing its tracking flags whenever `_isMaxModeActive` was true, actually releasing the hardware latch instead of only the in-memory state. This is a one-way risk-reduction fix (can only cause a needed release to be sent, never a new write behavior) and doesn't require new field validation under this project's evidence-gate rule, consistent with the board-`8A18` Max-mode fix shipped in 4.1.0. 3 new tests in `WmiFanControllerPerformanceModeMaxReleaseTests.cs` cover: the latch is released when switching away from an active Max hold, no redundant `SetFanMax` call is sent when Max mode was never active, and `RestoreAutoControl()` correctly finds nothing left to do afterward. Likely also resolves the spontaneous max/auto cycling symptom as a side effect (the firmware fighting a contradictory latched-but-told-otherwise state), though that hasn't been independently confirmed — see `docs/ROADMAP_v4.0.0.md` for detail.

## Fixed: GPU Power Boost Status Didn't Flag When the Displayed Level Doesn't Match Hardware

When a user has a saved GPU Power Boost preference (e.g., "Maximum"), `DetectGpuPowerBoost()` deliberately doesn't overwrite the UI's selected level with what's actually detected on the hardware, so a user's choice isn't silently reverted by a routine capability re-detection. GitHub #159 showed the consequence of this on a system where startup restore is disabled (or a reapply attempt fails): the level selector still shows "Maximum," the saved config still says "Maximum," but the hardware can genuinely still be at "Minimum" until the user manually reapplies it — and the status text read as a plain "Minimum (detected via WMI)," easy to miss as contradicting the selected level next to it.

**Fix:** when a saved preference exists and doesn't match the freshly-detected hardware level, the status text now says so explicitly — `"Minimum (detected via WMI; saved preference 'Maximum' not yet applied)"` instead of just naming the detected level. The selected level itself is unchanged (still respects the user's saved preference); only the status text's honesty improved. No test coverage added — `DetectGpuPowerBoost()` is deep, hardware-entangled code (concrete `HpWmiBios`/CIM dependencies, not behind a mockable interface) with no existing test infrastructure, consistent with how the Logitech and Razer fixes earlier this cycle were verified (build-clean + code review only).

## Fixed: EC GPU-Boost Fallback Claimed "Extended" Applied When It Cannot Be Distinct From Maximum

The roadmap's open question about the "Extended" GPU Power Boost tier (`ppab=2`, one step above "Maximum") has real field evidence now: board `8A44` (GitHub #159 reporter, full session logs attached) tried Extended 8 times via WMI — every attempt was accepted by the BIOS but readback came back `PPAB=1`, never 2. Extended does not reach beyond Maximum on this board's firmware.

The same logs caught a second, more actionable problem: when the WMI attempt fails, `SystemControlViewModel.TryApplyEcGpuBoost()` (the EC-register fallback for GPU boost) was reached next, and it reported success — `✓ GPU Power Boost set to: Extended via EC (experimental)` — even though nothing distinct happened. Reading the code confirms why: this fallback writes a single performance-mode register (`0xCE`) that only has 4 possible values (Quiet/Default/Performance/Extreme), and `"Extended"` was mapped to the exact same value (`3`, "Extreme") as `"Maximum"`. In the reporter's logs, the register was already at `3` from a prior Maximum attempt, so the "Extended" write was a pure no-op (`Performance mode already at 0x03`) — yet it still logged success as if a distinct, higher boost had been applied. This is the same EC-write call site flagged as a risk in the 4.1.5 roadmap notes ("Not Actioned This Release") but not previously confirmed to misfire on real hardware.

**Fix:** `TryApplyEcGpuBoost()` now refuses `"Extended"` outright instead of silently reusing Maximum's register value and claiming a distinct result — it returns `false` before touching the register, with a log line explaining why. `ApplyGpuPowerBoost()`'s final failure status is now level-aware: selecting Extended on hardware where neither WMI nor EC can deliver it now shows *"Not available - this BIOS doesn't apply Extended via WMI, and no distinct EC fallback level exists beyond Maximum"* instead of the generic "Failed - WMI/EC commands not supported on this model" message, which read as if EC support were simply missing rather than structurally incapable of representing this level. No control-availability changed for Minimum/Medium/Maximum — only the previously-false "Extended via EC" claim was removed.

**Not fixed / not covered by tests:** `TryApplyEcGpuBoost()`'s model gate is still a broad `model.Contains("OMEN")` substring match with no capability-database flag, same as before — untouched this release, still flagged for a dedicated pass. No test added: exercising this path requires `SystemInfoService.GetSystemInfo()` to report a live "OMEN..." model string, which hits real WMI with no mockable seam — consistent with how `DetectGpuPowerBoost()` was verified earlier this cycle (build-clean + code review only).

## Adopted: Board 8D87 Support, Telemetry Correctness, and Robustness Fixes (Community Contribution)

A community member (GitHub `tempestnano`) sent a branch built from real reverse-engineering of HP's own OMEN Gaming Hub binaries (decompiled, not obfuscated) combined with live measurement on one HP OMEN MAX 16-ak0098nr (board `8D87`). Full detail, including the evidence methodology, is in the roadmap's "Community Contribution" section and the branch's own `docs/8D87-EVIDENCE.md`. After a full file-by-file review (every changed file read, not just the branch's own write-up trusted), it was merged in — every change is either read-only telemetry/diagnostics, or a general correctness/robustness fix that doesn't depend on the 8D87-specific evidence. Nothing from the branch's own explicitly-gated "Tier 3" (writing raw EC memory to force GPU/CPU power beyond adapter spec) is included — that remains unimplemented in the branch itself, pending write-safety questions the contributor's own document leaves open.

**General correctness fixes (apply to more than just board 8D87):**
- `WmiFanController.SetPerformanceMode`'s V2-fan-command detection used to force any board whose model name contained both "MAX" and "OMEN" onto V2 fan commands, with no confirmation the board actually supports them — a blind name-substring assertion this project's own roadmap had already flagged as a problem. It now probes the firmware first (`ProbeV2FanCommands()`) and only switches when both V2 commands are genuinely accepted, falling back to whatever the firmware itself reported otherwise. One-way risk reduction: it can only stop a wrong forced switch, never introduce one.
- `HpWmiBios.GetGpuMode()` and `GetKeyboardType()` used to cast a raw wire byte straight to an enum; an out-of-range byte (seen for real on board `8D87`, which returns `0xFF` for keyboard type) produced an undeclared enum value that printed as a bare number and compared equal to nothing — neither a valid answer nor a recognizable failure. Both now validate the byte and return `null` for anything the enum doesn't declare.
- `GpuSwitchService.DetectCurrentMode()` inferred GPU mode from which adapter was actively driving a display — indistinguishable from "dGPU idled by RTD3" on a healthy Optimus laptop, which made a perfectly normal Hybrid machine intermittently report as Integrated-only. It now asks the firmware (`Legacy 0x52`) first when available, falling back to the existing adapter-activity inference only when the firmware can't answer.
- `FanVerificationService` used to log a fan-speed change as "✓ verified" purely on the BIOS echoing the level it was told to write — real evidence a command was accepted, not that the fan moved. On boards without a working tachometer this made verification incapable of ever failing. It now (a) explicitly rejects a non-zero requested speed that reads 0 RPM from a physical tachometer, and (b) logs level-only passes with distinct wording ("command accepted... fan motion NOT confirmed") instead of the same "✓ verified" phrasing used for a real RPM-corroborated pass.
- `PerformanceModeService.Apply()` used to unconditionally log "applied successfully" even when every effect path (EC power limits, WMI thermal-policy fallback, linked fan policy) declined to run — the same false-success class fixed twice elsewhere this cycle (Max-fan latch, EC GPU boost). It now logs exactly which effects were actually applied, or an explicit "nothing was applied" warning with the skip reason.
- The dashboard's battery cycle count was a hardcoded `"127"`/`"0"` and its remaining-life estimate a hardcoded `"~3.0 years"` — neither derived from the machine. A new `BatteryInfoProvider` reads real cycle count and capacity from `root\wmi` (the same source `powercfg`'s own battery report uses), shared between the dashboard and `HardwareMonitoringService` so they no longer run independent copies of the same WMI queries, cached 30 minutes since these values change on the order of once per full discharge.
- The monitoring-tab fan chart was plotting `FanEfficiency` (a 0-100 proxy) under an axis labeled "RPM" — a real ~2800 RPM rendered as "28". A new `FanRpmAverage` field carries the actual mean RPM for that chart; `FanEfficiency` is unchanged for whatever else still uses the 0-100 scale.
- `FanDiagnosticsViewModel.RunGuidedDiagnosticCommand`/`CopyGuidedResultCommand` were expression-bodied properties that constructed a **new** `ICommand` instance on every WPF binding evaluation — so the button bound to whichever instance existed at first load, and since nothing held a reference to raise `CanExecuteChanged` on it, "Copy Results" could never re-enable itself after becoming available. Now constructed once and explicitly re-queried when the relevant state changes.
- `DiagnosticsView`'s adapter-refresh and other read-only diagnostic queries are dispatched at `DispatcherPriority.Background` from `Loaded` rather than run inline, so opening the tab paints first instead of blocking on a WMI round trip (a real risk on a degraded WMI repository, where the legacy fallback path this can hit has no timeout at all).

**Board-`8D87`-specific corrections (OMEN MAX 16-ak0098nr, GitHub #117), all owner-measured on the hardware, not inferred from adjacent boards:**
- `MaxFanLevel` corrected `100` → `60` — this board reports thermal policy V1 and refuses the V2 fan commands outright, so fan levels arrive via the V1 krpm/100 path; at `100`, a 50% request wrote raw level 50 (≈5000 RPM, near maximum, not half).
- Real fan tachometers at EC `0x70`/`0x5C` (16-bit RPM) added as a read-only capability (`ModelCapabilities.EcFanTachometerOffsets`), corroborated against the V1 WMI fallback at four operating points to ~1%. Board-scoped: legacy single-byte offsets do **not** apply here (EC is memory-mapped, not port-offset), and on a neighboring board those legacy offsets land inside the ASCII serial number and decode to a believable-looking fake RPM — the new offsets are used only when a model's database entry explicitly supplies them.
- `"L5P"` removed from this board's performance-mode list — inherited from a sibling entry, but `HpWmiBios.FanMode` has no byte for it, so it could never actually be sent; requesting it silently fell through to Default.
- `SupportsAdvancedOptimus` corrected `true` → `false`, `SupportsUndervolt` corrected `false` → `true` (this part undervolts fine via AMD Curve Optimizer; the old `false` gave the wrong reason — "AMD path doesn't use Intel MSR" conflates transport with capability), `HasFourZoneRgb`/`HasLightBar` corrected (the four-zone commands drive this chassis's light bar, not the per-key keyboard, so "four-zone succeeded" was landing on the wrong physical surface), `SupportsTccOffset`/`SupportsOverboost` made explicit rather than left at misleading Intel-oriented defaults. `UserVerified` flipped to `true` — every board-specific field above is measured on the hardware, not inferred.
- Power-adapter awareness (`Legacy 0x0F`) and the full `Default 0x28` `SystemDesignData` capability block are now decoded (general capability, exposed for every board that answers them, not just `8D87`) and surfaced in Diagnostics and the diagnostics export — a user on an under-rated adapter previously saw only the symptom (GPU pinned well below rating) with nothing anywhere attributing it to the adapter.
- `HidPerKeyBackend`'s keyboard scan now also checks the Darfon vendor ID (`0x0D62`) in addition to HP's own — on this board the internal keyboard enumerates under Darfon, HP's keyboard ODM, and was completely invisible to the old HP-only scan. Two previously-guessed, never-confirmed PIDs (`0x054E`/`0x054F`) were removed. The real device found on this board (`0x0D62:0x54BF`) is deliberately **not** added to the writable device list — its lighting protocol hasn't been confirmed, and scanning for diagnostics is a different risk than writing to an unconfirmed device.

**Test coverage:** 92 new tests across 9 new test files (adapter/enum/SystemDesignData decoding, the 8D87 model-database entry, EC fan tachometer reads, fan verification honesty, GPU mode mapping, performance-mode no-op reporting, fan-chart units, battery info provider), plus additions to 3 existing test files. Full suite: 1097/1097 passing after integration.

**Not included / still gated:** the branch's own "Tier 3" — writing raw EC memory (via the ACPI port pair, not WinRing0/inpoutx64, which this project already removed over Defender detections) to force `OGHP`/`PROH` and unlock GPU power beyond adapter spec — is explicitly unimplemented in the branch, pending confirmation that the same port aliasing holds for *writes* (only reads have been verified) and a resolved safety-gating design. Not touched here either. See the roadmap for the full mechanism trace if this is ever picked up.

## Improved: UI Responsiveness (Fan Curve Editor, Dashboard, Window Chrome)

Standing user feedback that the UI feels laggy prompted a targeted audit of animation and redraw code (not a redesign) for concrete, scoped fixes. Three real, continuously-firing sources of unnecessary rendering work were found and fixed:

- **Fan curve editor was doing a full chart teardown/rebuild on every telemetry tick.** `FanCurveEditor.UpdateCurrentTempIndicator()` called `RenderCurve()` — a full `ChartCanvas.Children.Clear()` and rebuild of gridlines, axis labels, the ghost curve, the curve line, and every draggable point (each getting a brand-new `DropShadowEffect`) — just to move one vertical temperature-indicator line. This ran on every new thermal sample while the Fan Control tab was open, across all 3 `FanCurveEditor` instances at once (combined/CPU/GPU curves) — one of the most-used tabs, frequently open during active tuning or gaming. **Fix:** the indicator line and label are now tracked individually and swapped in place (removed and re-inserted at the correct z-order position, below the draggable points) instead of triggering a full re-render. Gridlines, curve line, fill, and points are now untouched by temperature updates.
- **Dashboard's critical-temperature pulse animation restarted on every telemetry tick instead of once.** `HardwareMonitoringDashboard.AnimateMetricIfCritical()` guarded against re-triggering with `textBlock.Foreground != Brushes.Red` — but the assigned brush is always a freshly-allocated `SolidColorBrush`, which can never reference-equal the static `Brushes.Red` singleton, so the guard never actually skipped anything. Every tick while CPU or GPU temperature stayed above 85°C, a new brush and a new infinite `ColorAnimation` were allocated and started — continuously, for as long as the system stayed hot, which is exactly when a game is running and frame-time smoothness matters most. **Fix:** the TextBlock's `Tag` now marks whether the pulse animation is already running, so it starts once per critical streak instead of every tick.
- **The whole main window was paying for a blur effect on every redraw, not just its own edge.** `MainWindow.xaml`'s root `Border` — wrapping the entire window content (title bar, sidebar, every tab) — had a `DropShadowEffect` applied directly to it. Combined with `AllowsTransparency="True"` (already forcing this window into software-composited rendering), stacking a blur pixel shader on the root of the whole visual tree meant every resize, drag, or content change anywhere in the window additionally rendered the entire subtree to an offscreen surface and ran a blur pass over it — a real, continuous cost on the single most common interaction (resize/move) for a shadow subtle enough most users wouldn't consciously miss. **Fix:** removed. The smaller, static brand-glow effect elsewhere in the sidebar is untouched.

No test coverage added — all three are WPF rendering/animation code with no existing UI-test infrastructure in this project (consistent with how other XAML-only changes have been verified this cycle: build-clean + code review). Not independently benchmarked in this environment (no realistic way to reproduce sustained thermal load or measure frame timing here) — these are structural fixes to code that was demonstrably doing more work than necessary, not fixes validated against a before/after frame-rate measurement.

**Not touched, lower priority per the same audit:** `GameLibraryView`'s game list sets `VirtualizingPanel.IsVirtualizing="True"` but its `ItemsPanel` is a plain `WrapPanel`, which doesn't implement virtualization — the attached properties are currently a no-op. Lower impact than the three above (most users' game libraries are short), and swapping to a virtualizing wrap panel needs either a custom panel implementation or a new dependency, both larger in scope than this pass. The monitoring-tab historical charts (`DrawChartOnCanvas`) and the General-tab `ThermalChart` sparkline do similar clear-and-rebuild work but are already throttled (5s and 100ms respectively) and suppressed when not visible, so the payoff for tightening them further is smaller.

## Improved: UI Responsiveness, Second Pass (Dashboard Fan Chart, a Leak, a Hot-Path Allocation)

A second audit pass, deliberately covering different ground than the first (fan curve editor / dashboard pulse animation / window shadow, above) rather than re-checking the same files:

- **`FanCurveChart` (the small chart on the Dashboard tab) had the identical full-rebuild-on-tick bug already fixed in the Fan Control tab's editor, independently.** `OnPointsChanged` called a full `ChartCanvas.Children.Clear()` + rebuild (gridlines, a LINQ min/max pass, every line segment and point marker recreated) on every single `CollectionChanged` event. `DashboardViewModel.UpdateFanCurvePoints()` fires that on essentially every telemetry sample, and switching to the Dashboard tab replays up to 50 historical samples one at a time — up to 50 full rebuilds in a single burst. **Fix:** throttled and coalesced with the same trailing-edge pattern already used by the Dashboard's other two charts (`LoadChart`/`GpuVcChart`) — 100ms, `Dispatcher.InvokeAsync` at Background priority.
- **`MemoryOptimizerView` leaked a `PropertyChanged` subscription on every `DataContext` reassignment.** It subscribed to its view-model's `PropertyChanged` both at construction (if `DataContext` was already set) and again on every `DataContextChanged` — with no unsubscribe from the previous view-model either time. A reassignment left the old handler live, each one accumulating another `UpdateMemoryBar()` call per property change. **Fix:** the view now tracks which view-model it's subscribed to and unsubscribes before attaching a new one.
- **`DashboardConverters.FanSpeedConverter` re-resolved two regex patterns from `Regex`'s internal static cache on every conversion**, in a binding path updated on essentially every telemetry tick. **Fix:** both patterns are now `static readonly`, compiled `Regex` instances.

No test coverage added — same reasoning as the first UI pass (WPF rendering/binding code, no existing UI-test infrastructure, build-clean + code review). Full suite: 1097/1097 passing after these changes.

## Improved: UI Responsiveness, Third Pass (OSD Overlay Per-Tick Brush Allocations)

A third audit pass, prompted by a follow-up sweep of the same category of bug rather than a new field report — deliberately different files than either of the first two passes.

- **`OsdOverlayWindow` allocated a brand-new, non-frozen `SolidColorBrush` every second for every status-colored readout it shows.** `UpdateCpuTempColor()`, `UpdateGpuTempColor()`, and `UpdateGpuHotspotTempColor()` each `new SolidColorBrush(...)`'d one of four fixed RGB values depending on which threshold band the reading fell in, called from `UpdateStats()` on the OSD's 1-second telemetry timer (`OsdStatsTimerIntervalMs`) — and the same pattern was independently repeated for the battery-percentage color and the network-latency color (the latter on its own 5-second timer). None of the six call sites needed a new brush at all: the same four RGB values (green/yellow/orange/red) recur across all of them, and the file already had the right pattern sitting a few lines away — `FpsGoodBrush`/`FpsWarningBrush`/`FpsCriticalBrush`, a set of `static readonly`, `Freeze()`d brushes built once via `CreateFrozenBrush()` and reused for the FPS accent color. The OSD overlay is the one window most likely to be on screen *specifically* while a game is running (that's its entire purpose), making this a real, continuous allocation during exactly the sessions where frame-time smoothness matters most — the same framing already used for the Dashboard pulse-animation fix in the first pass.
- **Fix:** added `StatusGoodBrush`/`StatusWarningBrush`/`StatusOrangeBrush`/`StatusCriticalBrush` (reusing the existing `FpsGoodBrush`/`FpsWarningBrush`/`FpsCriticalBrush` instances for the three colors already frozen, plus one new frozen orange) and pointed all six call sites at them instead of allocating. Pure allocation-elimination — the threshold logic and displayed colors are byte-for-byte unchanged.

No test coverage added — same reasoning as the first two passes (WPF binding code, no existing UI-test infrastructure, build-clean + code review). Not benchmarked, same caveat as the first two passes. Full suite: 1171/1171 passing after this change.

## Improved: Visual Polish — Tray/Toast Iconography, a Missing Notification, a Resource Cleanup

Prompted by feedback that the UI reads as "vibe-coded." Rather than guessing at subjective fixes, audited the style dictionary and several views for concrete, describable issues instead of vague restyling.

- **Tray menu and toast notifications were built from emoji, not icons.** `TrayIconService.cs` had 31+ emoji embedded directly in `MenuItem.Header` text (`"🔥 Max Fan"`, `"🔔 Recent Notifications ▶"`, `"🎮  OmenCore  v..."`), and `NotificationService.cs` had ~18 more across toast titles plus an entirely unused `TypeIcon` property. Windows tray menus and toast notifications conventionally use real icon glyphs, not colorful pictographs baked into text — no other Windows utility does this, including HP's own OMEN Gaming Hub, and rendering varies by the user's installed emoji font. ## Fixed: MainViewModel Shutdown Never Released the EC/WMI/NVAPI Handles It Acquired at Startup

Flagged as a known gap during this cycle's `MainViewModel`→`HardwareBringup` extraction ("deliberately not fixing five pre-existing disposal gaps... real behavior change, out of scope for a pure extraction") and picked up now that it's isolated: `MainViewModel.Dispose()` — called from `App.OnExit` on every normal quit — never called `Dispose()` on the EC access handle (`_ecAccess`, a `PawnIOEcAccess` wrapping a live PawnIO driver handle and a loaded native module), the WMI BIOS monitor (`_wmiBiosMonitor`), or the NVAPI service (`_nvapiService`, which owns the one documented-correct NVAPI shutdown call, `NvAPI_Unload()`). All three were long-lived fields, constructed once in `HardwareBringup` at startup and held for the app's entire lifetime, but nothing ever released them. A separate, smaller instance of the same gap: `HardwareBringup`'s own local `CapabilityDetectionService` (used once during startup capability probing, then never referenced again) held its own independent WMI BIOS wrapper that was never disposed either.

Since the process is exiting either way, the OS reclaims these handles regardless — this was never a live leak during a running session, and disposing them can't change any fan/EC/thermal *behavior* while the app is running (by the time `MainViewModel.Dispose()` runs, `FanService.Dispose()` has already restored BIOS auto-control and stopped its monitor loop). It is, however, the documented-correct shutdown for NVAPI specifically, and relying on process teardown instead of an explicit `Dispose()` for the PawnIO/WMI native handles is exactly the kind of thing that can turn into a real bug the next time this code is refactored (e.g. if `MainViewModel` is ever constructed/disposed more than once per process, which the ongoing DI-composition-root work could eventually make possible).

**Fix:** `MainViewModel.Dispose()` now disposes `_ecAccess`/`_wmiBiosMonitor`/`_nvapiService` at the very end of the method, after every other service's own disposal has run, each independently `try`/`catch`-guarded so one failing can't stop the rest (matching the defensive pattern `WmiBiosMonitor.Dispose()` already uses for its own per-counter cleanup). `HardwareBringup`'s local `CapabilityDetectionService` is now disposed immediately after its one-time startup probing completes, instead of being left for the GC finalizer. Pure resource-cleanup addition — no fan/EC/WMI/NVAPI *write* behavior changed, nothing runs earlier or differently than before, only extra release calls at the very end of an already-terminal path.

No new test added — exercising this specifically would need a mockable `IEcAccess`/`WmiBiosMonitor`/`NvapiService` seam that doesn't exist (same reasoning already used for other hardware-entangled shutdown code in this codebase), but every existing `MainViewModelTests.cs` test already constructs and disposes a real `MainViewModel` end-to-end, so the full suite passing is direct confirmation none of the three new disposal calls throw unhandled on this environment's hardware. Full suite: 1171/1171 passing.

## Traced, Not Fixed: Background Resource Conservation

Investigated whether the app's idle/tray CPU and WMI/EC traffic could be reduced, per a standing ask alongside the UI-responsiveness work. Two real, architectural findings — both intentionally **not** acted on this release, because both sit inside the actual thermal-polling pipeline that drives live fan control, which this project's evidence-gate convention treats as fan/thermal-*behavior*-adjacent even when the change is "just" a cache duration:

- **`FanService`'s own temperature polling defeats `HardwareMonitoringService`'s tray-mode backoff.** `HardwareMonitoringService` correctly backs its own cadence off from 2s (active) to 10s (tray-only), but `FanService.MonitorLoop` reads temperatures on its own independent 1-5s schedule against the same `WmiBiosMonitor`, whose shared read cache is a fixed 500ms regardless of tray mode (only the GPU-telemetry path currently respects `SetStaticTraySamplingMode`). Since FanService's fastest cadence always exceeds that fixed cache window, real WMI-BIOS/EC reads keep happening every 1-5s even while minimized and idle — tray mode currently saves nothing on this path. A safe-looking fix (widen the cache, or have `FanService` consume `HardwareMonitoringService`'s already-fresh sample instead of reading independently) directly changes how quickly the app notices a temperature change while running in the background, which is a real thermal-responsiveness question, not just an efficiency one — not applied without more design work and field validation.
- **The out-of-process `OmenCore.HardwareWorker` polls all sensors continuously regardless of OmenCore's own visibility state.** It launches unconditionally at startup (not lazily on first fallback need) and only slows its own ~500ms cadence down to ~1.5-3s after 15-30 seconds of nobody calling it at all — there's no signal path from OmenCore's tray/low-overhead mode into the worker process. Fixing this needs a cross-process cadence signal (e.g. a pipe command), a larger and riskier change than this pass's scope.

Two minor/contingent findings from the same pass, not acted on and not urgent: `LibreHardwareMonitorImpl.EnsureCacheFresh()` sync-blocks a threadpool thread on IPC, but is currently only reached via a low-frequency fallback path, not the steady-state hot path. `TemperatureRgbService` and `ScreenColorSamplingService` are fully-built, independently-polling services that are never instantiated anywhere in the app — currently zero runtime cost, flagged only so nobody wires one up assuming it's the current pattern (`LightingViewModel` already implements the same features off the shared telemetry stream with no extra polling).

2 new tests for the 8BCA disambiguation (confirms both the new AMD sibling resolves correctly and the original Intel entry still resolves for its own WMI model name). No test coverage for the culture fix or the bloatware rule removal — both are either a startup-only side-effect-free config call or a straightforward deletion with no new logic to cover.

## Adopted: Second Community PR Batch (tempestnano) — AMD SMU Transport, dGPU Sleep-State Fixes, Per-Key RGB, Process Lifecycle

Following the same file-by-file review discipline used for PR #162 earlier this cycle — every changed file read in full, every safety-relevant claim traced through the actual code rather than trusted from the PR description — six more of tempestnano's PRs were reviewed and merged this round. (A background review-agent batch was also dispatched for this same set; three of the four agents hit the account's monthly spend limit mid-review and produced unusable partial output, so those PRs — everything except #160/#161 — were reviewed directly instead, per the owner's explicit call once the agent failures were reported.)

The fix is correct and one-way-safe on its own terms — there was no working behavior to regress. **#166 — Stop waking a sleeping discrete GPU to poll it.** On Optimus/RTD3 laptops, OmenCore's own NVAPI/NVML polling was itself what kept the dGPU from ever reaching D3 — any query wakes the device to answer, then reports the state of a GPU that was asleep until asked, so it never got the chance to idle (costing 20-25W continuously for nothing). `GpuPowerStateProbe` reads the PnP power state via `cfgmgr32` (`DEVPKEY_Device_PowerData`), which is answered from OS bookkeeping and never touches the device, so it's safe to check on every poll. All three poll paths (`NvapiService`, `LibreHardwareMonitorImpl`, and the out-of-process `OmenCore.HardwareWorker`) now skip a confirmed-D3 dGPU. Verified the fail-open behavior directly: every error path returns `Unknown`, and `IsAsleep()` is only ever `true` on a positively-confirmed D3 read — a genuinely active, rendering GPU (which the OS reports as D0) is never mistakenly skipped. Not board-specific; benefits every NVIDIA-dGPU laptop.

**#167 — Stop the hardware worker when OmenCore exits.** Quitting the app left `OmenCore.HardwareWorker.exe` running for its full 5-minute orphan timeout, still polling hardware, because the graceful `SHUTDOWN` pipe message never actually reached it — `Dispose()` wrapped the stop sequence in an un-awaited `Task.Run`, and `App.OnExit` returns straight into process teardown before that task could get anywhere. Fixed with a bounded, blocking stop off the dispatcher thread, plus a by-process-name fallback lookup for the common case where the client doesn't own the worker's process handle (both the app and `WmiBiosMonitor` can each independently launch the worker before any client exists). Verified the safety scoping specifically: the by-name lookup is restricted to the current logon session (never reaches another signed-in user's worker) and gated on the calling client having actually attached to a worker first (a client that never connected has no claim on whatever worker happens to be running).

**#169 — Fix a real shutdown race over GPU performance counters.** `WmiBiosMonitor.Dispose()` enumerated a `Dictionary<string, PerformanceCounter>` that the live monitoring loop concurrently mutates (adding/removing counters as GPU engine instances come and go on a hybrid laptop) — a genuine `InvalidOperationException` race in production, not just a test artifact, since both sides run concurrently during normal app shutdown. Fixed with a dedicated lock, snapshotting to an array before the slow per-counter reads so `Dispose` is never queued behind them, and a second `_disposed` check inside the lock after the (unlocked) category enumeration to prevent a late repopulation from leaking counters.

**#165 — Per-key RGB and light bar for board 8D87.** The largest PR in the batch (36 files). `HidPerKeyBackend`'s protocol (inferred from OpenRGB) isn't this keyboard's — it's Darfon `0D62:54BF`, not the guessed PID `0x054F` — so a new `DojoPerKeyBackend` speaks the real protocol over the keyboard's two actual interfaces (a static-colour HID LampArray and the device's own onboard animation engine, mutually exclusive states of the same keyboard). Now asks the firmware first (`GetKeyboardLightingType()`) when available, falling back to the exact same old assumption — now honestly logged as an assumption — only when the probe itself doesn't answer.   - The new unelevated light-bar HID path and the new measured-layout per-key editor are both explicitly board-gated (`OmenBoard.SupportsHidLightBar`, allowlisting only `8D87`) and only ever consulted as a fallback when HP's WMI surface is unavailable — never displacing the existing elevated WMI path, so elevated behavior is unchanged regardless.

## Adopted: Adapter Power Override, APU Clamp Lift, and Per-LED Lighting for Every Board (Community Contribution, tempestnano)

A large follow-up submission from tempestnano (67 commits, ~42,000 lines, merging several feature branches built on top of the board-8D87 work already adopted this cycle) — reviewed file-by-file, the same discipline used for every community contribution this cycle, with one section held to a higher bar because of what it actually does.

**Adapter power override and APU clamp lift** (`AdapterPowerOverrideService`, `ApuPowerClampService`, `GpuRestartGate`, `AdapterClampLiftSettings`) — supersedes #168 above with a substantially more complete mechanism. On boards that clamp power when a lower-wattage-than-expected adapter is connected, two independent things get clamped: the discrete GPU (via a one-off ACPI notification the driver has no way to re-query) and the CPU (three of four AMD SMU power limits pinned low by AML paths outside anything this app already touches). Measured by the contributor on board 8D87 with a 280 W supply against a 330 W requirement: GPU enforced limit went 35 W → 80 W after a driver restart with the GPU drawing 79.93 W against it under load; CPU package power went from a 25 W pin to 51 W held across 40 samples over 12.5 minutes, tracked back to specific ACPI paths (`_REG`, `_Q32`) that reassert the clamp on resume/power events rather than on a timer.

Both halves default to off and are explicit, disclosed, one-directional actions:
- The GPU restart needs Administrator elevation, an explicit button press, and a confirmation dialog; it only proceeds when the dGPU is genuinely parked (checked via the PnP manager's own power-state bookkeeping, which costs nothing to read), and refuses rather than guessing when that can't be confirmed. An optional automatic mode (off by default) restricts itself further: AC power only, Hybrid/Optimus display mode only (never when the internal panel is driven by the dGPU), and re-checks parked state again immediately before pulling the device.
- The APU clamp lift writes the same four SMU limits the platform's own firmware would write — targeting the user's own already-configured STAPM setting if one exists, falling back to the firmware's own documented `Default 0x28` CPU-with-GPU budget for the SKU, never an arbitrary or invented ceiling — and re-applies only on the events that take it away (resume, supply change, app start), not on a timer. An optional automatic mode requires the connected adapter to cover at least 60% of the machine's stated power requirement before it's even offered.
- `StartupRestorePolicy.MayReapplyTuning()` is a new general safety check (applies to GPU OC reapply too, not just this feature): a confirmed tuning value's *unattended* startup-reapply authorization is automatically withdrawn for one boot after `LastShutdownProbe` (a read-only query of Windows' own Kernel-Boot 20 event) reports the previous session ended uncleanly — a crash, hang, or hard power loss. The value itself is never touched; the user re-confirms via the existing Test Apply → Keep flow.

**Why this needed a higher bar than the rest of this batch, and why it shipped anyway:** `GpuRestartGate`'s own documentation records that an earlier version of this exact mechanism crashed both `OmenCore.exe` and `OmenCore.HardwareWorker.exe` outright on its first real-hardware run — an `AccessViolationException` from a stale NVML device handle, a corrupted-state exception managed code cannot catch, found only by actually restarting a GPU on real hardware, not by any amount of code review. The current version fixes it with a two-part handshake (a cross-process marker file that stops new NVML calls from starting, plus a 16-slot named semaphore that's fully drained — meaning every in-flight call has returned — before the device is touched) that was traced by hand and holds up under review. But the SMU power-limit writes are gated by CPU family rather than by board, meaning this hands live SMU-write capability to several AMD families with zero field evidence beyond the one board this was measured on — the same pattern already restricted once this cycle via the Strix-Point-only gate on `SetStapmLimit`/`SetTctlTemp`. This is squarely this project's own Phase-D "hardware-gated, needs field evidence" territory. Flagged explicitly to the project owner, including the crash history and single-board-evidence caveats; merged per an explicit, informed owner decision to accept that risk rather than hold it the way #168 was held. `SetTctlTemp`'s existing Strix-Point-only gate was deliberately left untouched — nothing in this submission needs it broadened.

**Per-LED lighting for every board** (`KeyboardLayoutCatalog` + `KeyboardLayouts.json`, a `DojoPerKeyBackend` rewrite, `KeyboardMapEditor`) — a fundamentally lower-risk addition than the above (worst case is a wrong LED color, not damaged hardware, the same bar already applied to the per-key-RGB work merged earlier this cycle). The MCU's static colour map is one byte per LED, not per key — Space is five LEDs, backspace six — so a per-board mapping from key to LED positions is what makes "color one key" meaningful at all. Derived from HP OMEN Gaming Hub's own embedded layout tables by an external extraction tool, covering every OMEN/Victus per-key keyboard variant; only one (Dojo/Global, board 8D87) has actually been seen on hardware, and every layout entry carries its own `Verified` flag rather than a blanket claim. Also fixes a real bug in the previous per-key path: taking host control of the HID LampArray to paint per-key colours suppressed the MCU's own colour-map redraw, so the keyboard stayed frozen on the Fn-overlay frame after Fn was released until something else repainted it — the rewrite routes uniform/zone/per-key colour through the MCU's own map instead, which the MCU redraws by itself, so the picture survives the Fn overlay with no host involvement.

**Other fixes carried in the same submission:**
- A real worker-process bug, evidenced by an actual incident: `OmenCore.HardwareWorker`'s orphan watchdog only enforced its no-client timeout when it believed its parent process had already exited (`_parentAlive == false`), but that flag can stay incorrectly `true` forever if the parent's PID gets reused by an unrelated long-lived process, or if the parent is hung rather than exited. On 2026-08-08 this let an orphaned worker outlive its parent by 22 minutes, polling the discrete GPU twice a second on battery and waking it out of D3 every time, until the display driver's own watchdog timed out and bugchecked the machine (`0x116`, `VIDEO_TDR_FAILURE`). Fixed by gating the timeout on client silence alone, independent of the (inherently unreliable) parent-liveness guess.
- `App.OnStartup` now logs a PID/session/args line as the very first thing it does, before anything that can hang (RTSS detection enumerates processes; touching `Configuration.Config` loads and can rewrite the config file). A wedged startup previously left a zero-byte log file with no way to correlate it against the hardware worker's own log for the same incident.
- `KeyboardLightingService.Dispose()` now releases the light bar's HID LampArray back to autonomous/device control on shutdown — it was previously left in host-control mode after the app exited.

**Test coverage:** 95 new tests across 5 new test files (`GpuRestartGateTests` — including that a restart cannot begin while a poller is inside NVML, and that running out of slots is never misreported as a restart; `AdapterClampLiftPolicyTests`; `AdapterPowerOverrideServiceTests`; `ApuPowerClampServiceTests`; `AmdPowerLimitTests`), plus additions to `KeyboardMapGroupingTests`, `StartupRestorePolicyTests`, and `MainViewModelTests`. Full suite: 1266/1266 passing.

Two more field reports investigated thoroughly but not conclusively resolved — recorded honestly rather than shipping a guessed fix, consistent with how this project handles evidence gaps elsewhere.

Did not find a code-level bug via this review. **What would settle it:** the reporter's actual `config.json` content immediately after toggling a setting, and again after the reported reset — that would show whether this is a save-side problem (the write never happened) or something else entirely (a load-side or display-side issue this review didn't find).

## Fixed: Guided Fan Diagnostic Displayed Stale, One-Step-Behind RPM Estimates (GitHub #163 Follow-Up)

## Improved: Tuning Subsystems Honesty and Safety Pass (GPU Power Boost, GPU OC/UV, CPU OC/UV)

A full code review of the three tuning subsystems (`docs/TUNING-SUBSYSTEMS-REVIEW.md`) found several places where the app either reported something as applied when it wasn't, discarded a safety signal by defaulting it to a value indistinguishable from a real reading, or duplicated the same clamp constant across files where it could silently drift. This pass ships every finding that's a pure honesty/consolidation fix and needs no field validation, and explicitly does not implement two findings that turned out, on closer inspection, to be real hardware-write-path changes.

**Per-core CPU undervolt no longer silently drops the request.** `UndervoltOffset.PerCoreOffsetsMv` was accepted by the UI, clamped, saved to config, and printed into diagnostics bundles — but neither `IntelUndervoltProvider` nor `AmdUndervoltProvider` has ever had a per-core write path, so it was applied to nothing while the UI reported success. `UndervoltStatus` gained `PerCoreOffsetsRequestedButNotApplied`, surfaced through the existing undervolt warning banner, and `DiagnosticExportService`'s `tuning-safety.txt` now prints `PerCoreOffsetsAppliedToHardware: false (...)` whenever a per-core config exists. No per-core writes were implemented — this is a reporting fix only; per-core undervolt remains config-editable-only with no UI surface.

**Removed 40+ lines of permanently-unreachable code** in `AmdUndervoltProvider.SetTctlTemp` — an early-return already restricted every real call to `RyzenFamily.StrixPoint`, but the `switch` below it still listed fifteen other families that could never be reached.

**External undervolt-controller detection (XTU/DTT/ThrottleStop) no longer reports a fabricated `0 mV`** for controllers whose actual offset was never read — `ExternalUndervoltInfo.Offset` and `UndervoltStatus.ExternalCoreOffsetMv`/`ExternalCacheOffsetMv` are now nullable, with `null` meaning "detected but not read" instead of "confirmed zero." The detection sweep (several `ServiceController`/`Process.GetProcessesByName` lookups) is now cached for 5 seconds, since `ProbeAsync` can run more often than the periodic monitor loop (e.g. as an Apply/Reset preflight check).

**CPU vendor misdetection is no longer silent or permanent.** `CpuUndervoltProviderFactory.DetectCpu()` now logs when it falls back to the Intel default for either an unrecognized CPU or a failed WMI query — and a failed query (a transient condition) no longer permanently memoizes that guess, so a later call can retry instead of being stuck on it for the process lifetime. This factory's vendor result now also gates `ModelCapabilityDatabase`'s `RequiredCpuVendor` check (the #172 fix above), so a silent misdetection has more consequence than it used to.

**GPU clock/power/Curve-Optimizer clamp bounds are consolidated into `TuningGuardrails`** as a single source of truth, instead of being separate hardcoded literals in `NvapiService`, `AmdGpuService`, and `AmdUndervoltProvider`. Every existing numeric bound is preserved exactly (this is a pure consolidation, not a policy change) — including the fact that AMD's clock-offset clamp does not currently distinguish core from memory, which is now an explicit doc comment rather than an implicit accident. Added `TuningGuardrails.NarrowToPolicy()`, and used it to fix a real gap: `NvapiService`'s two NVAPI power-policy query sites previously trusted the driver-reported min/max percentage with no ceiling at all — they now can only narrow the app's policy bounds, never widen past them. `AmdGpuService.SetPowerLimit` gained an explicit guard against a driver-reported inverted range (previously would have thrown from inside `Math.Clamp`, masked by a generic catch).

**Not implemented, reclassified after starting:** two findings from the review (F11: routing `NvapiService.SetVoltageOffset` through the NvAPIWrapper path its sibling clock-offset setters use; broader GPU-OC/CPU-UV readback verification) turned out on inspection to require genuinely new, unvalidated NVAPI/SMU write-path code with no hardware in this environment to test against — not refactors of existing logic. Left as documented findings for a future pass with either real hardware or a contributor who can validate them, consistent with this project's evidence-gate policy for anything that changes what reaches silicon.

15 new tests (`TuningGuardrailsTests.cs`, `UndervoltStatusTests.cs`, `DiagnosticExportSnapshotTests.cs`). One of the new tests (`NarrowToPolicy_InvertedDriverRange_DoesNotThrowAndStaysWithinPolicy`) caught a real bug in `NarrowToPolicy`'s own first draft — its inverted-range fallback returned `(min, min)` where `min = Math.Max(reportedMin, policyMin)`, which is not itself guaranteed to fall inside `[policyMin, policyMax]` when `reportedMin` is far outside policy; fixed to collapse to `policyMin` instead.

A Discord report (Minecraftian14OP, board `8BCA`, OMEN 16-xf0xxx `xf0060AX`, Pop!_OS 22.04) described real hardware harm: fans never responded to any preset in the GUI's Fan Control tab ("Apply Once" did nothing, no error, tried every preset), the System Control tab's performance-mode apply failed outright ("No thermal profile interface found (board 8BCA)"), and — critically — this went unnoticed until the laptop black-screened and shut itself off from overheating during a real workload. ## Fixed: Per-Key RGB Brightness Slider Did Nothing on Boards With a Known Keyboard Layout (Board `8D87`, Community Report)

Reported on board `8D87` (OMEN MAX 16-ak0xxx) against the per-key RGB editor shipped earlier this cycle: moving the Brightness slider and pressing Apply changed nothing. The colours applied correctly; the brightness setting was inert at every value.

**Root cause:** the OMEN MAX keyboard has two lighting interfaces, and only one of them has a brightness channel. `mi_04` (HID LampArray) carries a per-lamp intensity byte. `mi_03` (the keyboard MCU's own 176-entry static colour map) does not — it is raw RGB, and the MCU draws exactly the bytes it is handed. `DojoPerKeyBackend` stored the slider's value in `_brightness` and applied it only where an intensity byte existed, which is `mi_04`.

That was correct when it was written. It stopped being correct when per-key painting moved to `mi_03` so the picture would survive the Fn overlay — after that move, `mi_04` is reached only as the fallback for a board whose lamp ids cannot be resolved to colour-map positions. On every board that *does* have a layout, which is every board the per-key editor lists keys for, `_brightness` was written and never read. The reporter's log shows the shape exactly: `Apply: 176 LEDs ledsOk=True, 0 keys keysOk=True` — the whole picture through the colour map, and zero lamps through the one path that scaled it.

Nothing surfaced this. The slider moved, the view-model held the value, the backend held the value, and the write returned `True` — there is no colour readback on either interface, so "accepted" was the entire software claim and it was accurate. Only the keyboard disagreed.

**Fix:** brightness is now applied as host-side arithmetic in `DojoPerKeyBackend.WriteColorMap`, the single point every colour map passes through on its way to `mi_03`, scaling each channel linearly (rounded to nearest) exactly as `mi_04`'s intensity channel scales a lamp. The unscaled map is retained so `SetBrightnessAsync` can re-send the same picture at a new level rather than compounding each change on the last dimmed copy. A new `_mcuShowsHostMap` flag tracks whether that map is what the keyboard is actually drawing, so a brightness change repaints a static picture but never interrupts a running device animation, never un-blanks a keyboard whose backlight is off, and never fights host lamp ownership — the existing "a running effect cannot be dimmed" behaviour, which is a hardware limit on this board, is unchanged and the UI already says so.

The MCU's own brightness command (`0x0C`) is still sent and still expected to fail here. Measured on `8D87`, it is not acknowledged at any payload value (`0`, `1`, `2`, `3`, `50`, `100`) while `0x03`, `0x83`, `0x09`, `0x0A` and `0x10` are all acknowledged through the same handle and the same frame builder. It costs one frame and is the right lever on a board that implements it. Its doc comment claimed to be unmeasured; it has been measured, and now says what was found.

Two honesty fixes alongside: `KeyboardLightingServiceV2.SetPerKeyBrightness` returned `false` silently for any non-`DojoPerKeyBackend` backend, and now logs which backend declined; `KeyboardMapViewModel` now reports that in the Apply status line rather than leaving a user to infer a dead slider from an undimmed keyboard.

8 new tests in `DojoPerKeyBrightnessTests.cs` pin the scaling: full intensity is byte-for-byte transparent across all 256 channel values (a rounding error there would tint every colour a user picks), zero is black, the scale is linear and monotonic, and the `channel * intensity` product never overflows the byte it is cast to. The device end cannot be tested — `DojoKeyboardMcu` is sealed over a raw handle and neither interface reads colour back — so the arithmetic is the last automatically checkable point. Hardware-exercised on board `8D87` through `LightingProbe --per-key --zones FF0000 --brightness N --commit`: the backend opens both interfaces, resolves the layout, and the scaled colour map is accepted at each level. Full suite 1296/1296, 0 build warnings.

## Added: Separate Whole-Keyboard and Per-Selection Brightness in the Per-Key Editor (Board `8D87`, Community Report)

Follow-up from the same reporter after testing the fix above. With brightness working, the single slider was visibly doing two unrelated jobs: it scaled the whole picture *and* drove the light bar, so "dim these four keys" had no expression at all and dimming the keys dimmed the bar along with them.

**Change:** the editor now has a **Whole keyboard** master and a **Selected** level, which multiply. The master remains the backend's, applied on its way to the wire; the per-cell level is applied in `KeyboardMapViewModel` and is a separate field rather than a rewrite of the painted colour — baking it into the hex would be lossy and one-way, since dragging a key to 10% and back to 100% would quantise away the colour the user picked. Light bar zones take a level too: HP's frame carries one brightness byte for all four zones, so per-zone dimming cannot go to the firmware and is the same host-side arithmetic as the keys, with the master still riding the byte.

The key caps preview their own level so per-key differences are visible while editing, and deliberately not the master — at master 3 the whole editor goes near-black and you cannot see what you are painting. The preview's rounding is pinned to `DojoPerKeyBackend.Scale` by a test; with no colour readback on this hardware, a disagreement between what the cap shows and what the key does has nothing to settle it.

**Also closes an inference with a hole.** The "no device effect consumes the effect record's brightness field" verdict rested on `[4]` reading back unchanged through every frame ever sent — but every one of those frames carried `0`, so a firmware treating `0` as "leave alone" would have looked identical to one that ignores the field. Measured on `8D87` through a new `LightingProbe --effect-brightness` flag: `60` and `160` were each sent in a `0x03` frame the MCU demonstrably consumed (effect became Wave, colour became `#FF0000` then `#00FF00`, speed and direction took) and `[4]` read back `200` unchanged both times. `160` is a value this firmware has itself been observed holding, so it is not an out-of-range guess. The verdict now stands on measurement rather than on the absence of a test, and `SetBrightness`'s doc comment says so.

13 new tests in `KeyboardMapBrightnessTests.cs`, covering the default (untouched cells stay at full), that dimming leaves unselected cells alone, that the painted colour survives a 100 → 5 → 100 round trip, that a mixed selection reports the neutral end rather than one member's value, and that the cap preview scales by exactly what the backend would send.

## Added: Colour Pickers for the Device-Effect and Light Bar Colours

Reported alongside the brightness work: the device-effects card and the light bar card accepted custom colours as hex text and nothing else, so choosing one meant already knowing its hex. The per-key editor has had a picker since it shipped; these two never got one.

**Change:** both cards now use the same `ColorPickerDialog` the per-key editor uses, with the same gesture — the colour swatch *is* the picker button, and the hex box stays beside it for typing an exact value. Reused rather than reimplemented, since two colour-picking implementations in one app is how they end up disagreeing about what a hex string means.

The swatches render on every keystroke, because the hex boxes bind with `UpdateSourceTrigger=PropertyChanged`, so they must survive the partial values typing walks through (`#`, `#F`, `#FF`…). They fall back to black rather than throwing. One of those intermediate states is not what it looks like and the tests now say so: WPF's `ColorConverter` reads four-character hex as `#ARGB` shorthand, so `#FF88` is a real colour rather than a parse failure and the swatch briefly shows it on the way to `#FF8800`. Found by asserting the obvious guess and watching it fail.

11 new tests in `DeviceLightingSwatchTests.cs`.

## Added: Curate the Keyboard's Own `Fn+1` / `Fn+2` Effect Cycle (Board `8D87`)

Pressing `Fn+1` on this machine changes the keyboard lighting, and nothing in OmenCore knew why. Measured on `8D87` by polling the MCU's `0x83` state read in-process at 10 Hz while the keys were pressed, with HP's `OmenCommandCenterBackground` stopped:

- **`Fn+1` and `Fn+2` are one control, not two** — next and previous through a single list. `Fn+3` through `Fn+0` do nothing to lighting.
- **The list holds what a host wrote to it.** Two entries in the observed cycle were this project's own probe writes, and an ordinary command `0x03` effect frame was enough to install one — no flash write needed.
- **One slot per effect type, holding that effect's last parameters.** Wave was written twice in one session, red then green, and only green appeared in the cycle. It is not an append-only history.
- **`0x0A StoreLightingToFlash` neither creates nor reorders slots.** It does what its name says and no more.

So the Fn keys are a usable hardware profile switcher, and driving them needs no command OmenCore did not already send.

**Change:** a new "Fn+1 / Fn+2 cycle" card on the Lighting page. Configure an effect in the card above it, press *Add to cycle*, repeat, mark one as *Showing*, then *Write to keyboard*. The staged set persists in `config.json`. Profiles written this way are recalled by the keyboard itself — with OmenCore closed, or uninstalled, or on a fresh Windows install.

Two firmware rules the plan has to honour rather than the other way round, both in `FnCyclePlan` where they can be tested: duplicate effect types collapse to the later one (the firmware would overwrite anyway, so sending both spends a frame on an entry nothing could recall), and the *Showing* profile is written **last**, because the keyboard displays whatever arrived most recently and there is no separate command to say which. Staging an effect and applying it go through the same record builder, so a profile in the cycle is byte-identical to the frame the user just watched Apply produce.

**Stated in the card rather than discovered later:** writing *adds to or updates* what the keyboard holds. There is no command to remove or reorder an entry, and `0x83` reads only the effect currently showing — never the list — so taking a profile off the staged list does not take it off the keyboard, and nothing in the UI could show that it is still there.

Swipe staged with a theme is warned about before any frame goes out (it has no preset palette on this firmware and renders black), and Audio Pulse is allowed with a note that it is fed live levels by the host, so in the cycle it shows a steady colour.

Board-scoped: measured on `8D87` with BIOS F.07 and keyboard MCU `0D62:54BF`. The card appears only where a backend can reach that MCU.

49 new tests across `FnCyclePlanTests.cs` and `DeviceLightingFnCycleTests.cs`.

## Fixed: Per-Key Colours Reverted the Moment OmenCore Closed (Board `8D87`, Community Report)

Reported as "the keyboard colors don't seem to stick if I close the program". Everything about the apply worked: colours applied, held perfectly while the app was open, and were gone the next time it launched.

**Root cause: Windows Dynamic Lighting, not OmenCore.** It is a second owner of every HID LampArray on the machine and it wins whenever no application holds the device. While OmenCore holds host control it is incidentally locking Windows out; `Dispose` hands the lamps back on the way down — correctly, because leaving `AutonomousMode = 0` set is what strands a keyboard dark until a power cycle — and Dynamic Lighting repaints within one refresh interval, 33 ms on this board.

The log is what rules OmenCore out as the culprit. `[KeyboardMap] Apply: 176 LEDs ledsOk=True, 0 keys keysOk=True` with `Layout Dojo/Global (176 LEDs, 99 keys)` — zero keys through `mi_04`, the whole picture through `mi_03`'s colour map, which the MCU holds and redraws autonomously. `DojoPerKeyBackend.Dispose` says as much itself and is correct in saying it. The picture should have survived, and did not.

Confirmed by the one clean discriminator available on hardware with no colour readback: with `HKCU\Software\Microsoft\Lighting\AmbientLightingEnabled = 1` the picture reverted on exit; with Dynamic Lighting disabled and *nothing else changed*, the same picture held.

**Change:** a new `DynamicLightingState` reads the master toggle and the per-device card, and the per-key editor shows an explanatory banner with a button that opens the Dynamic Lighting settings page. Read-only, deliberately: these are another feature's settings and the user owns them, so OmenCore explains rather than silently switching off a Microsoft feature to make its own look better.

Registering as a Dynamic Lighting–aware app was considered and rejected for this symptom. Ambient (background) control requires MSIX package identity — [Microsoft's guidance](https://learn.microsoft.com/en-us/windows/apps/develop/devices-sensors/lighting-dynamic-lamparray) states it is enforced by the AmbientLightingServer, which "only accepts connections from an AmbientLightingClient in a process with package identity" — and, decisively, control of either kind ends when the process ends. Neither foreground nor ambient registration produces a picture that holds with OmenCore closed.

## Added: Per-Key Pictures That Survive Closing OmenCore and a Power Cycle (Board `8D87`)

The counterpart to the fix above. Microsoft's description of a device Windows is not driving is that it "operates in Autonomous mode … the hardware falls back to default behavior as defined by its firmware" — on this keyboard that is the `mi_03` colour map, so making the map the firmware's default is the supported way to have a picture persist, not a way around Dynamic Lighting.

**Save to keyboard.** A new button beside Apply writes the picture and then stores it in MCU flash, so it survives a power cycle and shows with OmenCore closed or uninstalled. `StoreToFlash` already existed and was reachable, but only the Fn-cycle write called it, and that persists the effect record rather than a painted picture — no per-key apply flashed anything. It is a separate button rather than part of Apply because it is a real flash write: HP's own client passes `isWriteRegistry: true` on every per-key apply, which in an editor with a brightness slider would mean a flash write per drag.

**Config restore.** The picture is also saved to `config.json` as painted — colour and per-cell level kept apart rather than flattened, since baking the level into the colour is lossy and one-way — and repainted at startup. Where a per-key picture exists it takes precedence over the four-zone restore, because the two describe the same keyboard at different resolutions and a zone fill would erase a picture completely.

21 new tests. The load-bearing ones are in `PerKeyCellKeyAgreementTests`: saving and restoring compose a cell identity in two different files and agree only by convention, and the failure mode when they drift is silent — the restore matches nothing, the editor comes back at its defaults, and it is indistinguishable from the save never having happened. Those tests assert the two sides equal *each other* rather than a hard-coded string, since asserting the string would pass just as happily if someone changed one side and updated the test to match.

## Fixed: Misleading Comment Claimed the PawnIO EC Module Was Embedded in the Executable

`PawnIOEcAccess` caches the compiled `LpcACPIEC` module in a `static byte[]` whose comment read "Embedded LpcACPIEC.amx module binary". It is not embedded. `LoadEcModule` reads it from disk — `<appdir>\drivers\` or `C:\Program Files\PawnIO\modules\` — and `PublishSingleFile` does not bundle `None` content items, since `IncludeAllContentForSelfExtract` is deliberately off.

This costs nothing for anyone using the installer, which takes the publish directory with `recursesubdirs`. It matters for hand-assembled deployments: copying only `OmenCore.exe` loses EC access, undervolt and the APU clamp lift in one go, and the only visible symptom is the sidebar badge reading **No EC** — the PawnIO driver is installed and running, so every other check passes. The PawnIO installer creates no `modules\` directory, so there is no second place for it to be found.

**Change:** comment corrected to say where the module actually comes from and what breaks when it is absent.
