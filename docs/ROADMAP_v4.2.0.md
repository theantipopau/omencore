# OmenCore v4.2.0 Roadmap — Trust the Numbers, Then Make It Feel Fast

**Status:** Planning. Opened 2026-08-16, immediately after v4.1.7 was built and staged.
**Base version:** v4.1.7
**Predecessor doc:** `docs/ROADMAP_v4.0.0.md` — carried the 4.0.0 → 4.1.7 cycle. Items still open there are rolled forward into this document (see "Rolled Over From v4.0.0" below) and that document should be treated as historical record from here on.

---

## Why This Cycle Exists

v4.1.x was overwhelmingly a *correctness* cycle: safety gates, silent-failure fixes, honesty passes, and sixteen reviewed community PRs. It made the app tell the truth more often. It did not make the app **feel** good to use, and it did not fix the single thing users judge a fan-control app on: **is the temperature it shows me real?**

Two pieces of public feedback (r/HPOmen, 2026-08-16, on the v4.1.7 announcement thread) frame this cycle better than any internal audit did. Both are quoted in full because both are, on investigation, **substantially correct** — and one of them is correct in a way the codebase already knew about and had gated rather than solved.

> **/u/Fennel-Extra** — "I tried to use it several times on my Omen Transcend 14. But I always got bored just for two reasons. 1. The app is feels extremely slow to move. Feels even laggier than the OGH. 2. The fan controls are just completely crazy and don't really work as intended. For instance, I played any game and the program never adjusted the fan speed so it led to overheating and fps loss. Are they fixed now?"

> **/u/CharmingMeasurement1** — "For me, this app is clunky. It displays made-up temperatures—it can show the CPU at 36 degrees when it's over 80. The fan controls are illogical. I recommend Omenmon-reborn, where you can manually control the fans with 1-degree precision."

Neither of these is a vague vibe complaint. Each maps to a specific, locatable defect or design gap. That mapping is the backbone of this roadmap.

### What the feedback actually maps to

**"Shows the CPU at 36 degrees when it's over 80" — traced to a real, specific bug.**

`WmiBiosMonitor.GetAcpiCpuTemperature()` (`src/OmenCoreApp/Hardware/WmiBiosMonitor.cs:2525`) enumerates `MSAcpi_ThermalZoneTemperature` and **latches the first thermal zone it encounters** into `_cpuThermalZoneInstance`, permanently for the process lifetime:

```csharp
if (_cpuThermalZoneInstance == null)
{
    // First valid zone — use it as default
    bestTemp = tempC;
    _cpuThermalZoneInstance = instanceName;
}
```

A later zone can only displace that latch if its instance name contains `CPU`, `CPUZ`, or `TZ00`. Real HP ACPI zone names frequently match none of those (`\_TZ.TZ01`, `THRM`, `ACPI\ThermalZone\THM0_0`), and on many laptops the first-enumerated zone is a **skin/chassis/ambient** sensor that genuinely sits in the mid-30s while the CPU package is at 80°C+. WMI enumeration order is not contractually stable, so which zone wins can vary per boot.

There *is* an outlier guard — `MaxAcpiDeltaFromWmiC = 18.0` (line 117) rejects an ACPI reading more than 18°C from the current cached value — **but it is conditioned on `_cachedCpuTemp > 0`** (line 945). When the HP WMI BIOS CPU temperature is unavailable or zero, that guard does not apply, and the latched zone is accepted unconditionally as "CPU temperature". A board whose WMI BIOS path is weak or absent therefore displays a chassis sensor as its CPU temp, indefinitely, with no cross-check and no user-visible indication of which sensor is being trusted.

That is a precise, code-level explanation of "36 degrees when it's over 80" — and because fan curves consume this same value, **a wrong temperature is also a fan-control bug, not just a display bug.** This is the highest-priority item in this roadmap.

**"Never adjusted the fan speed" on a Transcend 14 — not a bug; the app genuinely cannot, and hides that badly.**

Both Transcend 14 database entries (`8C58` and `8E41`, `ModelCapabilityDatabase.cs:1426` and `:1448`) carry `SupportsFanCurves = false` and `SupportsIndependentFanCurves = false`. The Transcend 14 exposes a WMI *profile-only* fan interface with no real curve API. So on that reporter's hardware OmenCore is behaving exactly as designed: it will not run a curve, because it has no curve to run.

`docs/ROADMAP_v4.0.0.md` already recorded this once (GitHub #156/#149, "UX Confusion, Not the Bug It Looks Like") and concluded the Diagnostics tab explains it adequately. **That conclusion was wrong, and this feedback is the evidence.** A user who installs a fan-control app, plays a game, watches their laptop overheat, and has to go find a Diagnostics tab to learn the app was never going to touch their fans has been failed by the product, regardless of how correct the gating logic is. "The capability flag is accurate" and "the user was misled" are both true here.

**"Feels extremely slow to move. Feels even laggier than the OGH." / "clunky"**

Three UI-responsiveness passes shipped across 4.1.x, each fixing real measured problems (chart teardown per tick, a pulse animation restarting continuously, a window-wide blur on every resize, per-second OSD brush allocation). Users still describe the app as laggier than the thing it replaces. That means the passes fixed real bugs but did not address whatever dominates *perceived* responsiveness — most likely startup cost, view-switch cost, and the absence of any motion design at all, rather than steady-state frame time. This cycle treats perceived performance as its own workstream with its own measurements, not as a series of opportunistic fixes.

**"Omenmon-reborn, where you can manually control the fans with 1-degree precision"**

Worth naming plainly: a competing tool is being recommended specifically for *fan control granularity*. Not for features, not for polish — for the core thing this app exists to do. That is a direct competitive signal and it belongs in the record.

---

## Cycle Goals

Three headline pillars, in priority order. Pillar 1 outranks the others because a beautiful, fast UI displaying a wrong temperature is worse than useless — it is confidently wrong.

1. **Sensor truth, and the fan control that depends on it.** Make the displayed CPU/GPU temperature provably the right sensor, make the app say which sensor it is using, and make fan response follow from a trustworthy number.
2. **Perceived performance and motion.** Startup time, view-switch cost, transition smoothness, and a real reduction in idle CPU/RAM over long background sessions.
3. **Typography and visual identity.** Move to Roboto Condensed as the app font.

## Pillar 1 — Sensor Truth and Fan Control

**This pillar is partly evidence-gated.** Per the project's standing rule (`ROADMAP_v4.0.0.md`, "How To Tackle This", item 2), anything that changes fan/EC/thermal *behavior* on real hardware needs field validation before shipping. Diagnostic, display, and honesty work is exempt. Each item below is tagged accordingly.

### 1.1 Fix ACPI thermal-zone selection — **partly exempt, partly gated**

- **[Exempt — pure correctness] DONE.** Replaced the "first zone wins, latched forever" logic in `GetAcpiCpuTemperature()` with `WmiBiosMonitor.SelectCpuThermalZone()`, extracted as a pure, unit-tested function: prefer a zone still matching the previously-confirmed name, else a zone whose name hints at CPU (`CPU`/`CPUZ`/`TZ00`), else — only when genuinely ambiguous — the *hottest* of the unnamed zones, since the CPU is the one component virtually guaranteed to run hottest under real load. Critically, an ambiguous pick is **never latched**: every poll re-evaluates from scratch until a confident name match appears, so a single unlucky "which zone is warmest right now" guess can't get stuck the way the old first-index latch did. 14 new tests in `WmiBiosMonitorAcpiZoneSelectionTests.cs`, including a direct regression test reproducing the field-reported shape (cool zone enumerated first, hot zone second, no name hints). Full suite: 1302/1302. No hardware behavior changed for single-zone systems (still just uses the only zone, same as before) or for boards where a zone already matches a name hint — this only changes what happens on multi-zone, ambiguously-named systems, which is exactly where the bug lived.
- **[Exempt] Partially done.** Multi-zone selection reasoning is now logged (`[WmiBiosMonitor] ACPI CPU thermal zone: <name> (confirmed | ambiguous, using hottest reading) — all zones this poll: [...]`) whenever there's more than one zone and the selection changes, so a future field report is diagnosable from a log export instead of requiring a live repro. **Not yet done:** surfacing this in the structured diagnostics-export bundle itself (still log-only) — folded into 1.2 below, since both need the same "show every source side by side" UI work.
- **[Exempt] Deliberately not duplicated.** Investigated extending the 18°C outlier guard to apply when `_cachedCpuTemp == 0` — found `TryApplyCpuTemperatureFallback()` already does materially the same job downstream, and more thoroughly: it detects an implausibly-low cached temp under real load/power (`ImplausiblyLowCpuTempThresholdC`/`CpuLoadThresholdForAuthorityMismatchPercent` etc.), probes a secondary LibreHardwareMonitor-backed worker reading, and requires 2 consecutive confirmed-mismatch readings before switching authority. Adding a second, independent plausibility check inside `GetAcpiCpuTemperature()` itself would duplicate that pipeline stage rather than complement it. The zone-selection fix above reduces how often that downstream mechanism even needs to fire; it doesn't need to be redundant with it.
- **[Gated]** Any change to which source ultimately *wins* authority for a given board, since fan curves consume that value. Needs a before/after log from an affected machine.

### 1.2 Surface the sensor, don't just use it — **exempt**

The app already tracks `CpuTemperatureAuthoritySource` and `CpuTemperatureAuthorityReason` internally (`WmiBiosMonitor.cs:322-324`) and shows them only in deep diagnostics. Users cannot currently answer "where is this number coming from?" without exporting a bundle.

- **Dashboard: DONE.** Checked first and found the premise needed correcting again — `CpuTemperatureAuthoritySource`/`Reason` weren't "shown only in deep diagnostics" as originally written here, they were computed and read *nowhere at all*, not even by the diagnostics export. Added both to `MonitoringSample` (`CpuTemperatureSource`/`CpuTemperatureSourceReason`, populated in `WmiBiosMonitor.BuildSampleFromCache()`), then a `DashboardViewModel.CpuTemperatureSourceTooltip` combining source + reason into a plain-language tooltip on the CPU temperature chip, plus `IsCpuTemperatureSourceFallback` driving a small warning glyph when the trusted source is `LHM Fallback` — meaning the primary WMI/ACPI reading was recently rejected as implausible. Also fixed the diagnostics export's existing `[CPU Temperature Authority]` section, which — despite its name — only ever printed `MonitoringSource`/`Health`/`LastSampleAgeSeconds` (the overall monitoring backend) and never the actual per-tick sensor authority; it now does. 8 new tests (`DashboardViewModelCpuTemperatureSourceTests.cs`) plus 2 assertions added to the existing `MonitoringSampleCopyConstructorTests.cs`. Full suite: 1310/1310.
- **OSD: DONE, but not as a tooltip.** Checked before building and found the plan itself was wrong for this surface: `OsdOverlayWindow` applies `WS_EX_TRANSPARENT` unconditionally (one call site, no toggle) — it's genuinely click-through at all times, so a hover tooltip would never be reachable during actual gameplay, the OSD's entire reason to exist. Added `IsCpuTempSourceFallback` (same "trusted source is LHM Fallback" check as the Dashboard) driving a small always-visible `~` marker next to the CPU temp reading instead of a tooltip — glanceable, no hover required, minimal visual cost in line with Pillar 2's decluttering goal. No dedicated test: `OsdOverlayWindow.xaml.cs` is a real WPF `Window` with Win32 P/Invoke in its constructor and has no existing test coverage for any of its other `UpdateStats()`-assigned properties either (`CpuTemp` included) — this one-line addition matches that same established, build-verified-only tier rather than introducing a new one.
- **Guided-diagnostics side-by-side comparison: DONE.** A genuinely new feature rather than another "wire up existing data" fix — reading WMI BIOS, ACPI Thermal Zone, and LibreHardwareMonitor simultaneously on demand required real design, since the live monitor loop only ever tracks one *winning* source at a time. Added `WmiBiosMonitor.GetCpuTemperatureSourceComparisonAsync()`, deliberately read-only and side-effect-free: the ACPI read reuses the same `SelectCpuThermalZone` pure function from the earlier fix but is called with `latchedInstance: null`, so it can never race the background monitor loop's own `_cpuThermalZoneInstance`. New `ICpuTemperatureSourceComparer` interface (same shape as `IFanVerificationService`) keeps the new `TemperatureSourceDiagnosticsViewModel` unit-testable without depending on the concrete WMI-coupled class. New "Temperature Source Comparison" card on the Diagnostics tab: one button, one read-only result showing every source side by side plus which one is currently trusted and why, with a visible warning state when they disagree by more than the same 18°C threshold the live outlier guard already uses. Caught and fixed an invented, nonexistent `BoolToRunningLabelConverter` XAML resource before it shipped — verified every resource key used against the actual style dictionaries rather than assuming, after getting one wrong on the first pass. 24 new tests (`CpuTemperatureSourceComparisonTests.cs`, `TemperatureSourceDiagnosticsViewModelTests.cs`). Full suite: 1326/1326.

### 1.3 Stop silently doing nothing on profile-only boards — **exempt**

**Correction, Windows side: this premise was stale.** Checked `git blame` before building anything — the Windows Fan Control tab's "Profile-only" badge, header hint ("Select an OEM fan profile"), and `FanOwnershipDetail` explanation ("Profile-only firmware control; custom curves and fixed fan levels are unavailable") all landed in `b538316` (2026-07-08), part of the 4.0.0 cycle — over a month before the Reddit report this item was written from. It's on the Fan Control tab's own header, not buried in Diagnostics. The predecessor roadmap's GitHub #156/#149 conclusion ("the Diagnostics tab already carries correct explanatory copy") was itself outdated by the time it was written; this is now doubly confirmed correct. Nothing to build here — recording the correction rather than shipping a redundant "fix."

**Real gap found instead, on the Linux GUI (`omencore-gui`) — FIXED.** `FanControlViewModel.cs` had the mirror-image problem from a different cause: when `CanEditFanCurve=false`, the curve-editor cards collapse via `IsVisible="{Binding CanEditFanCurve}"` with no explanation — except a warning banner *does* exist (`ShowCapabilityWarning`/`CapabilityWarningMessage`, bound in `FanControlView.axaml:17-20`), so the "zero explanation" framing was also wrong on first read. The actual bug: the banner's "profile-only" message was a single hardcoded string for every profile-only sub-case — *"Use System Control performance profiles for cooling behavior"* — while `LinuxCapabilityClassifier`'s real, already-computed `Reason` (plumbed all the way to `SystemCapabilities.FanControlCapabilityReason` and then never read) correctly distinguishes two very different situations. Traced `SetPerformanceModeAsync`: on a board with no `thermal_profile`/`platform_profile` path (exactly [GitHub #99](https://github.com/theantipopau/omencore/issues/99)'s board `8E41`, confirmed via that issue's own attached diagnostics — `Thermal Profile Control: ✗ Missing`), the suggested "performance profiles" workaround falls through to `powerprofilesctl` or throws outright — it has nothing fan-relevant to do. Meanwhile `SetCpuFanSpeedAsync`/`SetGpuFanSpeedAsync` **do** work on that exact board class: they already fall back to `TryWriteHwmonPwmEnable` (the 4.1.7 GitHub #174 fix) before any profile-based path, and that call isn't gated behind `CanEditFanCurve` — so Max Fan / Emergency Stop is real, working guidance the banner never gave. **Fix:** `InitializeCapabilitiesAsync()` now prefers the classifier's real `Reason` text over the generic per-class string, and appends a truthful note that Max Fan still works as a coarse override when the class is `profile-only` — never claims it for `telemetry-only`/`unsupported-control`, where no write path exists at all. Build-verified only (no test project for this target, no Linux/OMEN hardware in the dev environment — same tier as prior Linux GUI fixes this cycle).

**Not the same bug as the Fennel-Extra Reddit report** — that reporter didn't specify Windows or Linux, and without their diagnostics this can't be conclusively linked to #99 or to board `8E41` specifically. Recorded as a real, separate, now-fixed issue found along the way, not claimed as resolving the original report.

This is a UX honesty fix of exactly the kind this project already values; it changes no hardware behavior whatsoever.

### 1.4 Close out the Max-level-floor bug — **gated, highest-value carryover**

Confirmed on four boards (`8A18`, `8A25`, `8E10`, `8D41`) and traced repeatedly across 4.1.x without a fix, because every candidate fix was a threshold guess. Board `8E10`'s multi-day log showed the re-assert loop firing every ~20s continuously while Max Fan Mode is engaged, plus a correlated (unproven) stutter complaint.

The real fix is a **design decision, not a threshold tweak**: should `ExpectedLevel` and the observed-peak reference be board-relative rather than nominal-max-relative, across *both* `FanVerificationService.IsLevelReadbackMatch()` and `WmiFanController.IsMaxModeTelemetryHealthy()`? Scope this properly in 4.2.0 rather than deferring again. Needs a sustained-Max-hold log with independent RPM evidence from at least one affected board.

### 1.5 Fan-control granularity — **gated, scoping only**

Directly prompted by the OmenMon-reborn comparison. Investigate what per-degree manual control would require on boards that genuinely support duty-cycle writes, and whether the current curve-point model is the limiting factor or the hardware interface is. Scoping and design in this cycle; implementation only with field evidence.

**Scoping done.** Traced all three layers the "1-degree precision" comparison could plausibly be about, rather than guessing which one OmenMon-reborn actually means:

1. **Temperature axis: already effectively unlimited, not the bottleneck.** `FanService.InterpolateFanSpeed()` does real slope-based linear interpolation against the live `double` temperature reading between whatever curve points exist (`omen-fan`-style: `speed = speed[i-1] + slope * (temp - temp[i-1])`) — it does not require a point at every degree to respond smoothly as temperature changes one degree at a time. A 3-point curve already yields a continuously-varying fan response, not a staircase.
2. **Fan-speed axis: quantized to whole percent, but that's not a real loss.** The interpolated result is `Math.Round`ed to an integer percent before being mapped to a raw hardware level. Cross-referenced against `MaxFanLevel` across the database (55-100 depending on board, each unit ≈100 RPM per the existing "krpm units" comment in `WmiFanController`): on boards near `MaxFanLevel=100`, one percent ≈ one raw hardware level — whole-percent rounding costs nothing beyond what the firmware can represent anyway. On lower-ceiling boards (55-63), whole-percent granularity is *finer* than the hardware distinguishes, so some adjacent percentages collapse to the same level — again no real precision lost, just a few redundant values.
3. **The real, hardware-level ceiling: `HpWmiBios.SetFanLevel(byte fan1Level, byte fan2Level)` writes a single byte per fan.** This is HP's firmware's own native step size (~100 RPM, "krpm units"). No change on OmenCore's side — curve model, interpolation, or UI — can produce true 1-RPM resolution through this WMI command, on any board, because the command itself doesn't accept a finer value. If OmenMon-reborn is actually hitting finer resolution, it would have to be through a different, unconfirmed interface (direct EC duty-cycle writes on boards that expose one) — not something to guess at without a board known to support it.

**Real, concrete limiting factor found: a hardcoded UI cap, not the model or the hardware.** `FanControlViewModel.AddCurvePointCommand`'s `CanExecute` is gated on `CustomFanCurve.Count < 10` — a flat 10-point ceiling on how many points a user can manually add to a custom curve, unrelated to either of the above. `FanCurvePoint.TemperatureC` is already a plain `int`; nothing in the data model or the interpolation logic assumes or requires a small point count.

**Recommendation, not implemented this pass:** raising (or removing) the 10-point cap looks low-risk on its own terms — it's purely additive (a user who doesn't add more points sees no change), doesn't touch automatic/default curve behavior, doesn't change how any WMI write or interpolation works, and doesn't affect any board's default profile. But this item's own gate explicitly says "implementation only with field evidence," so the cap stays at 10 until that's revisited deliberately rather than changed as a side effect of this scoping pass.

## Pillar 2 — Perceived Performance, Motion, and Footprint

### 2.1 Measure before optimizing — **exempt**

Three prior passes fixed real problems without moving the needle on user perception, which means the wrong thing was being measured. Establish real baselines first:

- **Startup time-to-interactive and per-tab switch cost: DONE.** New `StartupAndNavigationPerformanceTracker` (static, thread-safe, `Interlocked`/`lock`-free-read snapshot pattern matching the existing `RuntimeUiPerformanceCounters`) records two numbers automatically on every run, no profiling session required:
  - **Startup time-to-interactive**, anchored on the OS's own process start time (`Process.StartTime`, not `App.OnStartup`'s entry — that excludes real CLR/WPF init cost) through to `MainWindow.ContentRendered`, which fires exactly once per window lifetime after the first real paint completes. Wired in `App.xaml.cs`, normal (non-headless, non-start-minimized) launch path only, since "time to interactive" doesn't map cleanly onto a window that's deliberately not being shown.
  - **Per-tab switch cost**, wrapping `MainViewModel.SelectedTabIndex`'s setter (the one shared choke point every tab change goes through, whether from a click or programmatic navigation) with a `Stopwatch`, then resuming the measurement at `DispatcherPriority.Render` — the standard WPF technique for "wait until pending layout/render work has actually been flushed" — so the number includes both the synchronous cost (including any lazy ViewModel construction a tab triggers on first visit) and the render pass that follows it, without needing to instrument nine separate views individually. Accumulates count/average/max per tab rather than every sample, so it stays cheap for the life of the process. No-ops cleanly when `Application.Current` is null (headless test host) — confirmed the existing `MainViewModelTests` tab-switch tests still pass unchanged.
  - Surfaced in `runtime-performance.txt`'s diagnostics export under a new `[Startup and Navigation]` section, next to the existing dispatcher/projection counters it's meant to be read alongside.
  - 7 new tests (`StartupAndNavigationPerformanceTrackerTests.cs`) covering the accumulation math and the "only the first startup call counts" idempotency directly, with no WPF dependency needed for the pure-logic half.
- **Not yet done:** steady-state idle CPU over a multi-hour tray session, and working-set growth over the same period. The existing `runtime-performance-bounded.txt` bounded-sample mechanism (3 samples, ~12s window) proves the harness shape works but is far too short a window to answer either question; needs a longer-running, opt-in capture mode rather than a bigger one-shot snapshot.

Ship the harness, not just the numbers, so regressions are catchable later.

### 2.2 Motion and transitions — **exempt**

The app currently has essentially no motion design. Add a coherent, *cheap* transition system: view-change transitions, state-change easing on gauges and readouts, and skeleton/placeholder states so first paint never shows an empty or jumping layout. Constraints, learned from the animation bugs already fixed this cycle: every animation must be GPU-composited where possible, must never restart on unrelated property changes, must be disabled wholesale under a "reduce motion" setting, and must respect the OS reduced-motion preference.

- **Reduce-motion infrastructure: DONE.** Built the prerequisite the constraints above depend on, before any actual animation exists to gate. New `OmenCore.Utils.MotionPreference.ShouldReduceMotion()` combines an explicit in-app `AppConfig.ReduceMotion` toggle (new Settings entry, "Reduce motion") with the Windows-wide "Show animations" preference (`SystemParameters.ClientAreaAnimation`, the standard `SPI_GETCLIENTAREAANIMATION` mechanism) — which happens to be the same registry value `VisualEffectsOptimizer`'s existing "Best Performance" system tweak already writes, so running that optimization also quiets OmenCore's own future motion for free, without any code linking the two features together. Defaults open (does not reduce motion) if the OS read throws, rather than silently disabling animation for everyone on a read failure. The OS-preference check is injectable (`internal static Func<bool> OsAnimationsEnabledOverride`) so it's fully unit-testable without depending on the test-runner machine's own Windows animation setting. 4 new tests (`MotionPreferenceTests.cs`).
- **Not yet done: the actual animations.** No transition, easing, or skeleton-state work has shipped yet — deliberately. This project's standing rule is to live-smoke-test real UI changes in the actual app before calling them done, and this environment cannot launch `OmenCore.exe` (elevation/EC-write risk). Shipping animation code with only a build-clean check behind it — no live verification that it doesn't restart on unrelated property changes, isn't janky, or actually respects the toggle just built — would repeat the exact class of mistake this pillar exists to fix. Left for a pass where live verification is available; the infrastructure above means that pass can start on animations directly instead of also having to build the gating mechanism.

### 2.3 Idle CPU/RAM conservation — **gated (both known findings)**

Two architectural findings were traced in the 4.1.6 cycle and deliberately left untouched, both because they sit in the temperature pipeline that drives fan control:

1. **`FanService`'s independent polling defeats tray-mode backoff.** `HardwareMonitoringService` correctly backs off 2s → 10s in tray mode, but `FanService.MonitorLoop` reads temperature on its own 1–5s schedule against a shared 500ms read cache that ignores tray mode. Real WMI/EC hardware reads therefore continue on FanService's cadence while minimized — **tray mode currently saves nothing on this path.**
2. **`OmenCore.HardwareWorker` never learns the main app is minimized or idle.** It launches unconditionally at startup rather than lazily on first need, and only backs off after 15–30s of nobody calling it. There is no signal path from the app's tray state into the worker at all; fixing it needs a cross-process cadence command.

Both are real wins for the "conserve CPU/RAM" goal and both change how fast the app notices a temperature change while unattended — a thermal-responsiveness question with physical stakes. Design first (what cache bound is safe, how it interacts with hysteresis and thermal protection), then validate, then ship.

**Design done for finding 1.** Traced the actual sharing rather than assuming: `MainViewModel` constructs one `WmiBiosMonitor` instance (`bringup.WmiBiosMonitor`) and passes the *same* reference both to `HardwareMonitoringService` (as `IHardwareMonitorBridge monitorBridge`) and into `FanService`'s `ThermalSensorProvider` (`new ThermalSensorProvider(monitorBridge)`) — so there genuinely is one shared cache, not two independent ones that happen to have the same lifetime. `WmiBiosMonitor.ReadSampleAsync()` is unconditional: `if (DateTime.Now - _lastUpdate < _cacheLifetime) return BuildSampleFromCache();` else do a real `UpdateReadings()` hardware read, where `_cacheLifetime` is a fixed `TimeSpan.FromMilliseconds(500)` field with no tray-mode awareness at all. Since `FanService.MonitorLoop` polls every 1-5s (`MonitorMinIntervalMs`/`MonitorMaxIntervalMs`) and 500ms is shorter than that gap, essentially *every* FanService poll finds the cache stale and forces a fresh hardware read — independent of whatever cadence `HardwareMonitoringService` has itself backed off to. This confirms the roadmap's framing exactly: tray mode's 2s→10s backoff genuinely saves nothing on this path, because FanService's own faster loop keeps forcing real reads underneath it.

Proposed design, not implemented this pass:
- Give `WmiBiosMonitor` a settable cache-lifetime input (e.g. `SetCacheLifetimeHint(TimeSpan)`) instead of the fixed 500ms constant, and have `HardwareMonitoringService` push an update to it from the same place it already computes cadence (`UpdateCadenceTelemetry(TimeSpan cadence)`, which already derives `_trayOnlyCadenceInterval` vs `_activeCadenceInterval` and already excludes "active fan-curve work" from ever entering the tray-only state per its own `"tray-only: app minimized with no active fan curve/hold"` log line — that exclusion is exactly the hysteresis/thermal-protection interaction this item's own text asks to be designed around, and it already exists, just not propagated to the read cache).
- **Do not reuse `HardwareMonitoringService`'s full tray-only interval (10s) as the read-cache lifetime directly.** That interval is sized for UI-refresh purposes, which don't carry the same safety weight as thermal-protection response — `FanService.CheckThermalProtection()` still runs every MonitorLoop tick even in Auto mode with no curve active, and letting it work from data up to 10 seconds stale would be a real, if subtle, thermal-safety regression, not just a UI staleness question. The cache lifetime pushed to `WmiBiosMonitor` should be a smaller, deliberately-chosen cap (a candidate starting point: 2-3 seconds) — long enough to eliminate most of the redundant reads FanService's 1-5s loop currently forces, short enough that thermal protection's worst-case reaction time barely moves. The exact number is a validation question, not a design one — needs a tray-mode idle-CPU measurement before and after to prove the win, exactly as this item's own gate requires.
- This design changes zero behavior when the UI is active or a curve/hold is running (the existing 500ms lifetime stays a floor, and `HardwareMonitoringService` only reports an extended lifetime candidate for the same states it already treats as safe to back off from) — the only behavior at risk is worst-case detection latency for an unattended, curve-idle, tray-minimized session, which is precisely the scenario this item's evidence gate exists to validate before shipping.

**Design sketched, less verified, for finding 2.** `HardwareWorkerClient`'s named-pipe channel to `OmenCore.HardwareWorker` already carries distinct command messages beyond plain sample polling — `SendDisableBatteryAsync()` is an existing precedent for exactly this shape. A `SendCadenceHintAsync(TimeSpan interval)` command following that same pattern, sent whenever `HardwareMonitoringService`'s own cadence changes, would let the worker adjust its poll timer immediately on a real signal instead of only inferring idleness after 15-30 seconds of silence. Not traced as deeply as finding 1 — the worker's own poll-loop internals weren't read in this pass — so this is a shape, not a full design; needs the same before/after idle-CPU measurement as finding 1 before shipping.

### 2.4 Dead-code and allocation cleanup — **exempt**

- **`TemperatureRgbService` and `ScreenColorSamplingService`: DONE, deleted.** Both were fully-built services with independent polling loops, confirmed via a repo-wide grep to have **zero references anywhere outside themselves** before deletion — `ScreenColorSamplingService` specifically is superseded by the very similarly named but actually-wired-up `ScreenSamplingService` (`LightingViewModel`'s real ambient-lighting path), and `TemperatureRgbService` duplicated functionality `LightingViewModel` already implements off the shared `HardwareMonitoringService.SampleUpdated` stream. - **Guardrail comment on `LibreHardwareMonitorImpl.EnsureCacheFresh()`: DONE.** Added an XML-doc `<remarks>` block explaining the sync-over-async IPC block (bounded to 500ms via `WaitAsync`) is only safe today because every caller (`GetCpuTemperature`/`GetGpuTemperature`/`GetCpuLoadPercent`/`GetGpuLoadPercent`/`GetCpuPowerWatts`/`GetGpuPowerWatts`) sits on the LHM-fallback path, invoked at most once per monitoring tick — and explicitly warns against adding a per-tick or UI-thread call site here without first making the path genuinely async, tying it back to Pillar 2's "feels laggy" framing so a future contributor has the *why*, not just a warning.
- **Background-thread-flavored coordinator: DONE.** New `BackgroundPollingCoordinator`, structurally identical to `UiPollingCoordinator` but backed by a real `System.Threading.Timer` instead of a `DispatcherTimer`, fanning out through the same already-tested `PollingScheduler` both share — this class adds only the background-timer plumbing around it, no new scheduling logic. Base cadence set to 1000ms rather than the UI coordinator's 500ms, since background polling has none of the "must feel responsive to render" pressure the UI cluster has, and halving the wake-up frequency is a small real win toward 2.3's idle-CPU goal. Added a reentrancy guard (`Interlocked.CompareExchange`) that `UiPollingCoordinator` doesn't need — `DispatcherTimer` processes ticks serially on one thread, but a plain `Timer` will keep firing on schedule even if a previous callback is still running, so a slow subscriber must not be allowed to pile up concurrent `Pump()` calls; a skipped tick is safe since `PollingScheduler` tracks each subscription's own due time independently. Unlike `UiPollingCoordinator` (untestable here without a live WPF `Dispatcher`), this class has zero WPF dependency and could be driven end-to-end with a real timer in the headless test host — 3 new tests (`BackgroundPollingCoordinatorTests.cs`) cover real thread-pool firing, disposal, and subscription-count bookkeeping, on top of `PollingScheduler`'s existing fake-clock coverage.
- **Not done: migrating `ProcessMonitoringService` itself.** Checked before assuming it would just slot in — it doesn't cleanly. Every service already on `UiPollingCoordinator` has a *fixed* cadence; `ProcessMonitoringService` deliberately changes its own poll interval at runtime (2s when a game is active, 10s idle, or a slower WMI-eventing reconciliation interval), and neither `PollingScheduler` nor this new coordinator currently support changing an existing subscription's interval — only subscribe-with-a-fixed-interval and dispose. Forcing it in today would mean unsubscribing and resubscribing on every active/idle transition, which is exactly the kind of behavioral change to a service that drives real game-profile switching that this project's own standing rules say needs to be verified live before shipping, not guessed at. Left as a deliberate next step: either extend `PollingScheduler` to support updating a live subscription's interval, or accept the resubscribe-on-change cost as the price of consolidation - a real design decision, not a small typing task.

### 2.5 General UI audit (prompted directly, 2026-08-19) — speed, clarity, visual presentation

Asked directly whether there were further UI optimizations available, beyond the items already tracked above. Investigated several concrete angles rather than brainstorming:

- **`GameLibraryView`'s virtualization was silently dead — FIXED.** The games `ListBox` had `VirtualizingPanel.IsVirtualizing="True"`, `VirtualizationMode="Recycling"`, and `ScrollUnit="Pixel"` all explicitly set, but its `ItemsPanel` was overridden to a plain `WrapPanel` — which doesn't implement virtualization at all, so every one of those properties was a silent no-op. Every detected game got a full visual tree built and kept alive regardless of scroll position; for a large Steam/Epic/GOG library (100+ games isn't unusual) that's real, measurable cost on every visit to the Games tab, and a plausible unaccounted-for contributor to the working-set growth Pillar 2.1 flagged as unexplained. **Fix:** removed the `WrapPanel` override entirely, falling back to `ListBox`'s real default (`VirtualizingStackPanel`), which correctly honors the virtualization properties that were already there. This changes the visual layout from a wrapping card grid to a single-column list — reflowed the per-item `DataTemplate` from three stacked rows (name / badges / executable) into one horizontal row per game, which is also a real readability win on its own (more of the library scannable per screen without scrolling), not just a side effect of the virtualization fix. Every binding, style, and trigger in the template is unchanged — only the layout container and row shape moved. Build-verified only: this environment cannot launch `OmenCore.exe` to visually confirm the reflowed row layout renders as intended (elevation/EC-write risk, standing rule), so this should get a look on first real run.
- **Tab-switch content lifecycle — checked, already correct, nothing to fix.** Hypothesized that WPF's `TabControl` might be discarding and rebuilding each tab's entire visual tree on every switch-away-and-back (a well-known WPF footgun, and a plausible explanation for "tabs feel slow"). Traced `MainWindow.xaml.cs` before claiming this: `EnsureTabContentCreated()` + an `_initializedTabs` tracking set already lazily construct each tab's content exactly once, on first visit, then leave `TabItem.Content` populated permanently — WPF's `TabControl` naturally keeps that content alive (just visually disconnected, not destroyed) when switching away, so revisiting any previously-opened tab is already free. Recorded here specifically so this hypothesis doesn't get re-investigated from scratch next time someone asks the same question.
- **`MainWindow.xaml`'s own comment already documents and avoids the "window-wide blur" class of bug.** Checked for a regression of the previously-fixed "blur/shadow effect on every resize" issue — found instead that the fix's reasoning is preserved as an explicit comment (`AllowsTransparency="True"` + `WindowStyle="None"` already forces layered-window software compositing; stacking a `DropShadowEffect` on the whole window on top of that would re-render the full subtree to an offscreen surface and run a blur shader on every redraw). The two `DropShadowEffect` instances that do exist in this file are scoped to small, fixed-size elements (a 36x36 icon border, a header card), which don't carry that cost. No regression found.

## Community Comparison: OmenXHub (MasonDye/OmenXHub, MIT) — Discord Suggestion (Trirez, 2026-08-19)

Trirez (the same reporter as [GitHub #163](https://github.com/theantipopau/omencore/issues/163), board `8BCA`) reported that OmenXHub's fan control and keyboard lighting both work on their board, and suggested a deep-dive comparison. Cloned and read the source (MIT licensed — more permissive than OmenMon-Reborn's GPLv3, checked before reading anything) rather than assuming from the suggestion alone. Following this project's own established practice for external sources (see the OmenMon-Reborn "Safe Emulation Policy" note under board `8E9A` below): extract facts and re-implement independently in OmenCore's own architecture, not port code — doubly relevant here since even MIT permits copying, but this codebase's own conventions (DI, logging, capability database) don't transplant cleanly regardless of license.

**Shipped: fan curve share codes.** OmenXHub has a compact "share code" concept for pasting a curve into a chat message rather than attaching a file. OmenCore already covers file-based curve sharing (`FanControlViewModel.ExportPresets`/`ImportPresets` — a saved `FanPreset` already carries its `Curve`), so a full duplicate export/import path would be redundant; the one genuinely incremental piece was the pasteable string. New `OmenCore.Utils.FanCurveShareCode` (independent implementation — OmenCore's own percent-based `FanCurvePoint` model and format, not OmenXHub's RPM-based one) plus two new buttons on the curve editor ("Copy Code" / "Paste Code"). Rejects malformed input outright rather than partially applying it. 15 new tests. Pure data serialization, no fan-control behavior touched — exempt from the evidence gate.

**Checked and confirmed NOT a gap: temperature smoothing.** OmenXHub uses EMA smoothing + a hysteresis threshold + a max step-down rate before curve lookup. `FanService.SmoothCurveTemperature()` already does an equivalent job with a different technique (max-rise/max-drop-per-evaluation clamp, with an explicit high-temperature bypass so smoothing can never delay a genuine thermal emergency). Different math, same goal, already shipped — not a gap to fill.

**Checked and confirmed NOT a gap: EC overwhelm on periodic writes.** A comment in OmenXHub's `OmenHardware.SetFanLevel` records a real, specific finding: sending a full multi-step reset sequence (`SetMaxFanSpeedOff` → zero → target) on *every* periodic timer tick, rather than only on an actual mode transition, overwhelms the EC on AMD laptops and leaves the fan stuck at zero or unresponsive. Checked `WmiFanController.SetFanSpeeds()` directly: OmenCore's steady-state path already sends a single `SetFanLevel` write per tick and only calls `SetFanMax(false)` conditionally (`if (_isMaxModeActive)`), with an explicit comment ("Avoid redundant SetFanMax(false) writes during steady-state curves") recording the same lesson independently. Already correct.

**Flagged, not implemented — needs validation before any action:** a second comment in the same file claims raw EC fan-level bytes below 10 (roughly <500 RPM) risk a firmware "bounce back" on HP's EC — their default curve floors are deliberately set at 600 RPM specifically to stay clear of that boundary. This is a specific, plausible, but third-party hardware claim about a general HP EC behavior, not something confirmed against any board this project tracks. Not implemented as a live floor/clamp — that would be a fan-control behavior change requiring the same evidence-gate treatment as any other EC-write change, and the claim itself hasn't been corroborated independently. Worth watching for in future field reports (a curve authored with a very low first point causing erratic behavior near that boundary would corroborate it).

### Re-verification pass (2026-08-19, prompted by a "triple check" request) — two corrections and three new findings

Re-read the OmenXHub source properly rather than trusting the first pass. **Two claims above were wrong and are corrected here; the rest held up.**

**CORRECTION 1 — "OmenXHub has no per-board capability database at all" was WRONG.** The first pass searched for `ProductId`/`BaseBoard`/`SystemSku` and found nothing outside `LibreHardwareMonitor`, and concluded there was no board gating. That conclusion was wrong because it searched for OmenCore's own vocabulary. OmenXHub *does* gate on board identity — it just sources it from HP's own assembly as `DeviceModel.ThisSystemID`, not from its own SMBIOS read. Confirmed board-specific logic:
  - `OmenHardware.GetThermalPolicyVersion()` carries a **V0 blacklist** — `{ "8607", "8746", "8747", "8749", "874A", "8748" }` — boards whose SystemDesignData byte 3 *claims* ThermalPolicy V1 but which must be forced back to V0.
  - `App/OmenLighting.cs` has a hardcoded `if (DeviceModel.ThisSystemID == "8E41")` special case in its per-key keyboard open path.
  - `DeviceModel.FeatureByte`, `IsOldOmenProduct`, `IsHP`, and `PerformanceControlHelper.GetPlatformSku()` are all used for further gating.
  The corrected conclusion: OmenXHub's board handling is *thinner* and outsourced to HP's DLLs, not absent. It does not maintain a per-board capability matrix the way OmenCore's `ModelCapabilityDatabase` does, but "no board gating whatsoever" was a factual error.

**CORRECTION 2 — the HP-SDK dependency is far broader than "keyboard lighting uses HP's own SDK".** OmenXHub embeds and redistributes **14+ HP/vendor proprietary binaries** as `EmbeddedResource`s (per `OmenSuperHub.csproj`): `HP.Omen.Core.Common`, `HP.Omen.Core.Model.Device`, `HP.Omen.Core.Api`, `HP.Omen.Core.Model.DataStructure`, `HP.Omen.Core.Utilities`, `HP.Omen.Core.Logger`, `HP.Omen.Logger`, `HP.Omen.Logger.APIs`, `PerformanceControl.dll`, `OmenFourZoneLighting.dll`, `OmenLightingSDK.dll`, `McuSDK2.dll`, `SMBiosSDK.dll`, `NvidiaApi.dll`. The whole application is built on HP's OGH assemblies, not just its lighting path — `OmenHardware.cs` itself opens with `using HP.Omen.Core.Model.Device.Models;`. This makes the "OGH-independence" trade-off much starker than first reported: adopting OmenXHub's approach wholesale would mean OmenCore depending on (and redistributing) the very software stack it exists to replace. The redistribution-licensing question flagged earlier applies to all 14, not one.

**Also noted: OmenXHub is itself a derivative** — its README states it is "based on and primarily derived from OmenSuperHub", and its root namespace and `.csproj`/`.sln` are still `OmenSuperHub`. OmenSuperHub is already referenced elsewhere in this project's notes; treat the two as one lineage when comparing.

**NEW FINDING 1 (actionable, evidence-gated): the ThermalPolicy V0 blacklist.** OmenCore reads thermal policy the same way OmenXHub does — `ThermalPolicy = (ThermalPolicyVersion)result[3]` from SystemDesignData (`HpWmiBios.cs:823`) — but has **no equivalent override list** for boards that misreport it. Confirmed by grep: none of `8607`, `8746`, `8747`, `8749`, `874A`, `8748` appear anywhere in OmenCore's source. If those boards genuinely misreport V1, OmenCore would send V1-shaped commands to V0 firmware on them. **Not implemented:** thermal policy version selects which EC/WMI command shapes get sent, so this is squarely fan-control behavior under the evidence gate — and these are all older boards (the `874x` range and `8607`) with no OmenCore field reports to corroborate against. Recorded as a concrete, checkable hypothesis for if a report ever arrives from one of those six boards.

**NEW FINDING 2 (already covered, no action): capability derivation from SystemDesignData bits.** `GetSupportedPerformanceModes()` derives which performance modes to expose from SystemDesignData byte 4 (bit 0 = SW fan control, bit 1 = turbo/extreme support) rather than a static table. OmenCore already reads and exports exactly these (`power-adapter.txt`'s `SW fan control support` / `Extreme mode support` lines come from the same `0x28` structure) — not a gap.

**CORRECTION 3 — the EC "bounce back" claim is weaker than first reported, and self-inconsistent.** Chased the source comment properly this time. Its own cross-reference (`OmenHardware.cs:205-208`) points at `IsCleanCreekSupported`, i.e. unrelated code — a stale line reference. More importantly, the claim is internally inconsistent under OmenXHub's own units: call sites convert with `SetFanLevel(rpm / 100, rpm / 100)`, so level byte 10 is **1000 RPM**, not the "<500" the comment asserts in the same breath. There is no enforcing clamp at that boundary either — the only floor in the codebase is `ClampRpm`'s unrelated 500 RPM parse guard. Verdict downgraded from "plausible, needs validation" to **"unsubstantiated folklore in a comment, do not act on"**. Correctly not implemented.

## Community Comparison: OmenCtl (yunusemreyl/OmenCtl, GPLv3) — "Max TGP unlock" Discord Report (Eric, 2026-08-19)

Eric reported trying OmenCtl and that it "unlocked Max TGP for nvidia gpus… they even explain how they did it on their github", linking both OmenCtl and OmenXHub. Investigated both, since the claim was ambiguous about which project it referred to.

**License note, and why it matters more here:** OmenCtl is **GPLv3**; OmenCore is **MIT**. Copying GPLv3 code into this project is not merely against convention, it is legally impossible without relicensing OmenCore in its entirety. Facts and observed behavior only — the same policy already applied to OmenMon-Reborn, but with real teeth this time.

**The OmenCtl "cTGP unlock" turns out to be the ordinary performance-mode switch, not a distinct unlock.** Their own `documentation/ARCHITECTURE.md` (§4, "Execution Flow: Set Performance Mode") traces it end to end: the daemon writes `1` to `/sys/devices/platform/hp-wmi/thermal_profile`; the kernel `hp-wmi` driver packages that into ACPI `_SB.WMID` with `CommandType = 0x11` (ThermalControl); and then — their words — "the BIOS receives the ACPI payload. It raises the cTGP … of the NVIDIA GPU from 80W to 115W, increases the CPU PL1/PL2 power limits, and instructs the Embedded Controller to apply an aggressive internal fan curve." In other words the TGP raise is a **firmware side-effect of setting the thermal profile**, which OmenCore already does. There is no separate unlock command to adopt.

**This is genuinely useful anyway — it corroborates an existing OmenCore hypothesis.** The long-running "GPU Power Boost unlocked in 4.1.5 but doesn't reach OGH's wattage" item (traced across `8A25`/`8A44`, still open) has assumed the missing wattage lives behind some GPU-boost WMI path OmenCore isn't calling. OmenCtl's trace supports a different reading: on their hardware the wattage comes from the *thermal-profile* command's firmware side-effects, not from a discrete GPU-power call at all. Worth re-examining that item against this framing before more field-testing effort goes into the GPU-boost path specifically.

**NEW FINDING 3 — and this is the actual "unlock", but it is in OmenXHub, not OmenCtl, and OmenCore should not adopt it.** `App/GpuAppManager.cs`'s `ChangeDBVersion()` ("DB" = Dynamic Boost) does the following: extracts an embedded NVIDIA **`nvpcf` driver** (`nvpcf_sys.sys` / `nvpcf_inf.inf` / `nvpcf_cat.CAT`, pinned to version `31.0.15.3730`, dated 08/28/2023) from its own resources; force-installs it with `pnputil /add-driver … /install /force`; then force-*uninstalls* every other nvpcf driver version present with `pnputil /delete-driver … /uninstall /force`. `CheckDBVersion()` gates this on the NVIDIA driver being between `537.42` and `610.47`. NVPCF is NVIDIA's Platform Controllers and Framework component — the piece that enforces the OEM's Dynamic Boost policy. So the mechanism is: **pin NVIDIA's power-policy driver to an old version that doesn't enforce the restriction.**

  This is a real explanation for a real mystery — it plausibly accounts both for the "can't reach OGH's wattage" item above *and* for [GitHub #137](https://github.com/theantipopau/omencore/issues/137)'s `nvidia-powerd` log line ("Client (presumably SBIOS) has requested to disable Dynamic Boost DC controller"): the cap may be enforced by NVIDIA's driver stack, not by HP's WMI at all. That reframing is worth keeping.

  **Recommendation: do not implement.** This is not an evidence-gate deferral, it is a decline on the merits. Redistributing NVIDIA driver binaries is almost certainly outside NVIDIA's redistribution terms; force-uninstalling a user's current display-power driver with `/force` can leave the graphics power stack in a state the user did not ask for and may not know how to restore; and pinning a 2023 driver silently blocks future NVIDIA fixes on the affected machine. A tool that manages fans should not be swapping the user's GPU drivers underneath them. If the wattage question is worth pursuing, the honest path is the WMI/firmware one already being investigated — not this.
